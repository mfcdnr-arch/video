# 04. Тесты

В проекте три уровня проверки перед релизом: **регрессионные unit-тесты**
(pytest: математика биллинга и кампаний, плейлисты и показы, код агента),
**smoke-тест** (сквозной, против живого стека) и **UI/E2E-тест** (браузерный
прогон панели). Для работы без боевого сервера есть **локальный стенд
разработки** — `dev_stand.sh` (§0).

---

## 0. Локальный стенд разработки — `dev_stand.sh`

Обычный стек `docker-compose.yml` с надстройкой `docker-compose.dev.yml` под
отдельным именем проекта **`dsdev`** (свои тома — данные боевого стека и чужих
проектов не затрагиваются). **Только для разработки, на боевом сервере не
используется.**

```bash
bash dev_stand.sh up      # собрать и поднять стенд (+ миграции)
bash dev_stand.sh down    # остановить, данные сохраняются
bash dev_stand.sh reset   # остановить, СТЕРЕТЬ тома и поднять заново (чистая БД)
```

- Панель — **`http://127.0.0.1:8088`**, порт открыт **только на loopback**
  (у admin стенда известный пароль, из локальной сети стенд виден быть не
  должен). NTP наружу не публикуется.
- Вход — `admin`, пароль в файле **`.dev_admin_pass`** (создаёт `dev_stand.sh`,
  файл в `.gitignore`; значение — сид миграции 001, принудительная смена пароля
  на стенде снята). На сервере `install_server.sh` генерирует случайный пароль.
- Контейнеры называются так же, как на сервере (`ds_api`, `ds_postgres`, …),
  поэтому `smoke_test.sh` и `migrate.sh` работают со стендом без правок.
  Боевой стек и стенд на одной машине одновременно не поднять.
- После `reset` БД пустая — ни экранов, ни роликов; тесты, которым это нужно,
  заводят свои данные сами и убирают их (см. §3).

Пароль в команды подставляйте так, чтобы он не попадал в историю и вывод:

```bash
SMOKE_ALLOW_BROADCAST=1 ADMIN_PASS=$(cat .dev_admin_pass) bash smoke_test.sh
ADMIN_PASS=$(cat .dev_admin_pass) DS_URL=http://nginx bash ui_test.sh
```

`SMOKE_ALLOW_BROADCAST=1` включает в smoke шаг «Общий эфир» (§2): он ставит эфир
на **все** экраны сети, поэтому **только на стенде** — на боевом сервере переменную
не задавайте (шаг сам пишет «пропущено» и не трогает эфир).

## 1. Регрессионные тесты (pytest) — `server/tests/`

### Что это и зачем
Автотесты, которые защищают **«денежную» и учётную математику** от случайных
поломок при будущих правках:
- **биллинг** — расчёт суммы счёта по тарифу (за показы / за минуты), округление
  до копеек, разбор дат периода, преобразование объёмов из `play_log`, итог с
  учётом скидки/доплаты;
- **кампании** — план/факт (план = цель × прошедшие дни), процент выполнения,
  недобор, переходы статусов (scheduled/active/finished/paused), границы дат по
  МСК, дневная детализация;
- **контроль монитора** — разбор `/sys/class/drm/*/status` агентом (в том числе
  «статус неизвестен» и виртуальные выходы, которые нельзя принимать за
  отключённый монитор) и правило тревоги на сервере;
- **карточка рекламодателя** — границы московских суток в UTC: ошибка на три
  часа тихо перенесла бы показы соседних суток в чужой период, а значит и в
  чужой счёт и эфирную справку;
- **плейлисты** — развёртка повторов ×N, мягкие предупреждения («подряд»,
  «доля», «дубли»), «общий час» для режима «по очереди»; создание и замена
  роликов плейлиста одним запросом (всё или ничего);
- **показы по датам** — даты и целые часы, статусы (запланирован / идёт /
  закончился / остановлен), поиск пересечений, решения «заменить» / «по
  очереди» / «оставить „…“» (yield: уступить показу или переопределению,
  цепочки уступок только к старшим, устаревшие решения о более новых показах
  не действуют), выбор плейлистов на экран в текущий час, расписание недели,
  подстановка решений при правке (свои или перевёрнутые решения показов,
  сохранённых позже), разбор строк БД, тело и ответы API;
- **дубли в медиатеке** — группировка роликов по md5, ответ 409 и главное:
  отклонённая загрузка не оставляет ни файла на диске, ни записи в БД;
- **агент** (`agent/tests/`) — повторы ×N в списке для плеера, срок действия
  `active_until`, повторный запрос ленты на стыке часов, выбор файлов
  текущего плейлиста, защита очистки диска от сбоя запроса списка файлов (§1.1).

Раньше это проверялось только вручную при каждой доработке. Теперь одна команда
подтверждает, что формулы не «поехали».

### Как устроено
Тесты **не требуют реального Postgres**: сессия БД подменяется лёгким моком
(`FakeDB` в [`conftest.py`](../../server/tests/conftest.py)), который возвращает
заранее заданные строки. Проверяется именно **чистая математика** над этими
данными. Корректность самих SQL-запросов проверяет smoke-тест против живого
стека (см. §2) — это разные уровни, они дополняют друг друга.

### Как запускать
Одной командой из каталога проекта:

```bash
bash run_tests.sh
```

Скрипт [`run_tests.sh`](../../run_tests.sh) сам ставит dev-зависимости (`pytest`)
в работающий контейнер `ds_api` и прогоняет `server/tests`. Запускать можно
**после любого обновления/пересборки** — воспроизводимо.

`pytest` **не входит** в production-образ (он не нужен для работы системы) —
dev-зависимости вынесены в
[`server/requirements-dev.txt`](../../server/requirements-dev.txt). Эквивалент
вручную:

```bash
docker exec ds_api pip install -r /app/requirements-dev.txt
docker exec -w /app ds_api python -m pytest tests -q
```

Ожидаемый результат — все тесты зелёные, например:
```
315 passed in 0.44s
```

> В `docker-compose.yml` каталог `agent/` смонтирован в `ds_api` как `/agent`
> (только для тестов) — поэтому тесты разбора сигнала монитора, которым нужен
> код агента, выполняются. Если запускать pytest в образе без `/agent`, они
> пропускаются (`307 passed, 1 skipped`) — это не ошибка.

> Установка `pytest` в контейнер **эфемерна** — теряется при пересборке образа
> (`docker compose up --build`). Это норма: перед прогоном просто повторите шаг 1.

> Настройки pytest — в `server/pytest.ini` (там же глушится постороннее
> предупреждение passlib про устаревший модуль `crypt` в Python 3.11+ — к нашему
> коду оно отношения не имеет).

### 1.1. Тесты агента — `agent/tests/`
Отдельный набор: он проверяет код мини-ПК и от сервера не зависит. Файлы:
`test_playable.py` (повторы ×N и порядок в списке для mpv), `test_active_until.py`
(срок действия показа, повторный запрос ленты на стыке часов),
`test_current_playlist.py` (какие файлы агент берёт из ленты, в т. ч. при
истёкшем сроке), `test_cleanup_guard.py` (сбой запроса списка файлов — сеть,
не 200, не JSON, не список — **не стирает ролики**: очистка пропускается,
синхронизация не падает и ничего не качает; успешный пустой список остаётся
«ничего не нужно», скрытые файлы и подпапки не трогаются), `test_play_count.py`
(журнал показов: каждый повтор баннера и короткого ролика — отдельный показ по
смене записи плейлиста mpv, без двойного счёта на стыке роликов; замер
состояния mpv на поддельном IPC). Нужен только
Python с `pytest`; `ds_agent` читает конфиг при
импорте, поэтому тесты подкладывают временный `config.ini` и подменяют
`requests` — сеть и mpv не требуются.

```bash
docker run --rm -v "$PWD/agent":/a:ro -w /a python:3.11-slim \
  sh -c 'pip install -q pytest && python -m pytest tests -q -p no:cacheprovider'
```
Ожидаемый результат: `62 passed`.

### Когда запускать
Перед каждым релизом и после любых правок в `routers/billing.py`,
`routers/campaigns.py`, `routers/playlists.py`, `routers/placements.py`,
`playlist_rules.py`, `placements_logic.py`, `placements_store.py` и в коде агента
(`agent/`). Быстро (доли секунды) — можно гонять хоть на каждый коммит.

## 2. Smoke-тест — `smoke_test.sh`

Сквозной прогон **против живого стека**: проверяет, что все 7 контейнеров живы,
работает вход, здоровье API и полный цикл «экран → медиа → плейлист →
расписание», а также доступность модулей (дашборд, отчёты, биллинг, кампании,
модерация, уведомления). Сюда же входят новые плейлисты и показы: проверка
повторов `/playlists/check`, создание плейлиста одним запросом, замена роликов,
**дубли** (повторная загрузка → 409 со сведениями о ролике, `allow_duplicate`,
список дублей, на диске не остаётся лишнего) и **показы** (предпросмотр, создание,
список, правка, неделя, остановка и отмена на новом экране) и **что экран играет
и качает**: показ на текущий час на тестовом экране → лента
`/schedule/minipc/{id}` по `X-Token` экрана отдаёт `active_source = placement` и
`active_until` = следующий целый час, ролик показа появился в `/files/list/{id}`;
после «Остановить» показа нет ни в ленте, ни в списке закачки. На том же часе —
**одно пересечение**: второй показ без решения → 409, с «Заменить» — в ленте
он; предпросмотр правки (`exclude_id`) отдаёт сохранённое решение второго, а
для первого (старшего) — перевёрнутое решение второго («оставить»); после
правки на «Оставить „…“ на это время» (yield) лента снова отдаёт первый показ,
а в списке показов — строка «уступает». Все тестовые данные создаются с
префиксом `SMOKE_` и удаляются в конце.

**Общий эфир** (шаг «Общий эфир: срок «до ЧЧ:00»») идёт на **все экраны** сети, поэтому
выполняется только при `SMOKE_ALLOW_BROADCAST=1` (стенд); без переменной печатается
«эфир на все экраны — пропущено» и ничего не включается. Шаг запоминает, что шло
в эфире, включает свой плейлист `SMOKE_bc_…` до следующего целого часа (час и ожидаемый
срок считаются в `ds_api` по МСК, при 23 час окончания = 24), проверяет `GET /broadcast`
(`is_on`, `until_at`), запись в журнале и срок на дашборде (`broadcast_until`). Глазами
тестового экрана (X-Token): пока плейлист эфира пуст, экрану нечего играть — лента
не отдаёт эфир (экран не гаснет); с роликом — лента отдаёт `active_source = broadcast`
и `active_until` = срок эфира, ролик эфира есть в `/files/list/{id}`, симулятор пишет
«общий эфир «…» до ЧЧ:00». Затем: час окончания, не позже текущего, и 25 → 400;
неизвестный плейлист → 404; старый вызов без тела (`?playlist_id=N`) = «до отмены»
(«Общий эфир сменён», `active_until` = null); выключение — лента не отдаёт эфир, ролика
эфира нет в списке закачки. В конце прежнее
состояние эфира возвращается (даже если проверка упала или скрипт прервали), плейлист
проверки удаляется. Само истечение по времени (Celery `expire_broadcast` раз в минуту)
smoke не ждёт — оно покрыто pytest (`test_broadcast.py`), а на стенде проверяется
вручную: сдвинуть `until_at` в прошлое в таблице `network_broadcast` и через минуту
увидеть в журнале «Общий эфир завершён по времени».

```bash
cd Video_miniPC_v16.2_modular
bash smoke_test.sh                           # боевой сервер и стенд: без шага «Общий эфир»
SMOKE_ALLOW_BROADCAST=1 bash smoke_test.sh   # только стенд: с шагом «Общий эфир»
```

Код возврата `0` — можно выпускать; иначе число упавших проверок. Ожидаемый
итог — `пройдено 117, провалено 0`, а со `SMOKE_ALLOW_BROADCAST=1` (стенд) —
`пройдено 131, провалено 0` (число проверок растёт вместе с тестом).
Остальные ветки с пересечениями и решениями («по очереди», переопределения,
цепочки уступок) smoke не проходит — они покрыты pytest и E2E (§3).

## 3. UI/E2E-тест панели — `ui_test.sh`

### Зачем отдельный уровень
Главный вывод пилотного развёртывания: **почти все дефекты панели нашлись
только живым кликом**. Кнопка звала неверный HTTP-метод (405 при создании
экрана), падала в JS или молча ничего не делала — а `smoke_test.sh` при этом
был зелёный, потому что проверяет эндпоинты, а не интерфейс.

### Что проверяет
1. Вход в панель под администратором.
2. Открытие **всех 14 разделов** левого меню (заголовок сменился, вью не
   отдало «Ошибка: …»).
3. Нажатие **всех «безопасных» кнопок** каждого раздела — открыть форму,
   вкладку, фильтр, отчёт, модалку. Список действий **белый и перечислен
   поимённо** в `ui_tests/ui_test.js` (`SAFE_ACTIONS`): удаление, отправка
   форм, включение эфира, OTA, команды экрану и выгрузки файлов не нажимаются
   никогда. **Добавили новую кнопку — допишите её в список**, иначе она в
   прогон не попадёт.
4. Цикл **экрана** с уборкой за собой: создать → токен и ID показаны →
   копирование токена → виден в списке → удалить.
5. **Просмотр ролика**: клик по миниатюре в Медиатеке открывает окно с `<video>`
   или `<img>`, Esc закрывает.
6. **Дубль при загрузке**: тот же файл через форму → окно «Такой ролик уже есть
   в медиатеке» (название существующего, три кнопки) → «Отмена» → копии в
   медиатеке нет. 409 сервера здесь ожидаем и провалом не считается.
7. **Плейлист целиком**, как это делает человек: «+ Плейлист» → название →
   поиск по части названия → галочка → «+» ×4 (повторы ×5, появилось
   предупреждение «подряд», кнопка «Создать всё равно») → «Создать и
   отправить →» → «Куда и когда»: «Выбрать экраны» → только свой тестовый
   экран `E2E_стенд_…`, завтра (МСК), 10–11 ч → пересечения (если есть —
   «Заменить», «ко всем» при двух и больше) → «Отправить на экраны» → в
   карточке плейлиста строка «запланирован» (тестовый экран, 10:00 – 11:00);
   «✎ Изменить ролики» и «📤 Отправить на экраны» открывают окна и закрываются
   по Esc → Расписание → «Экран» → **«По датам»**: сетка, листание ‹ ›, клетка показа завтра в 10:00 → карточка
   показа («запланирован»), «Сегодня» → в карточке плейлиста **«Отменить»** →
   плейлист удалён.
8. **Карточка рекламодателя**: открывается и все четыре вкладки (обзор,
   эфир, качество доставки, ролики) рисуются без ошибок.
9. **Изоляция роли «рекламодатель»** — самая дорогая ошибка раздела. Тест
   заводит настоящую учётку с ролью `advertiser`, входит ею в отдельном
   окне браузера и проверяет: в меню только его кабинет; `/advertisers`,
   `/minipc`, `/billing/invoices`, `/users` и чужая карточка отдают 403;
   свой кабинет открывается. Учётка и её кабинет удаляются в конце.
10. Индикатор монитора (бейдж 📺) отрисован на карточках экранов.

**Тестовые объекты.** Для плейлиста нужны экран и одобренный ролик, а на
чистом стенде (`dev_stand.sh reset`) их нет, поэтому прогон сам заводит экран
`E2E_стенд_…` и картинку-ролик `E2E_ролик_…` (категория «служебный контент» —
одобряется без модерации) и в конце убирает **всё, что создал, — даже если
проверка упала** (плейлист вместе с показом удаляется по названию). Поэтому
прогон проходит на пустой базе.

> **Осторожно: E2E — для локального стенда (§0) или стека без живых экранов.**
> Тестовый показ (завтра, 10–11 ч) прогон отправляет **только на собственный
> экран** `E2E_стенд_…`, а не на «Все экраны сети»: настоящие мини-ПК не получают
> его ни в ленту, ни в список закачки — даже если прогон оборван. Но прогон
> заводит в панели свои объекты (экран, ролик, плейлист, учётку рекламодателя),
> и на боевом сервере операторы увидят их в списках и журнале.
> Если прогон **оборван жёстко** (kill, таймаут docker, падение Chromium — тогда
> уборка в `finally` не выполняется), тестовые объекты остаются в панели.
> Удалите вручную по именам (все — с суффиксом `<STAMP>` — время прогона
> ЧЧММСС по UTC):
> - плейлист `E2E_плейлист_*` — вместе с ним удаляется его показ на тестовом
>   экране (Плейлисты → 🗑, панель предупредит «стоит в N показах»);
> - ролик `E2E_ролик_*` и, если он успел загрузиться, `E2E_дубль_*` (Медиатека →
>   Общая медиатека);
> - экран `E2E_стенд_*` (Экраны); и `E2E_экран_*`, если оборвало цикл экрана;
> - если оборвало проверку рекламодателя — учётка `e2e_adv_*` (Настройки) и
>   кабинет `E2E Рекламодатель e2e_adv_*` (Медиатека; удаляется отдельно).
> Экран `E2E_стенд_…` — не настоящий мини-ПК, на диски экранов сети ролик не попадал.

Кнопки «Просмотр» (`mprev-open`), «По датам» (`schedule-mode-dates`) и
«следующая неделя» (`schedule-week-next`) входят в белый список; слепой
прогон закрывает открывшиеся окна клавишей Esc.

Провалом считается не только упавшая проверка, но и **любая ошибка в консоли
браузера, необработанное JS-исключение или ответ HTTP ≥400** — именно так
выглядели дефекты, которые ловили руками.

### Как запускать
> Запускайте на стенде или стеке без живых экранов — см. «Осторожно» выше.

```bash
bash ui_test.sh
```

Chromium на сервер не ставится: прогон идёт в одноразовом контейнере
официального образа puppeteer, подключённом к сети стека (панель видна как
`http://nginx`). Первый запуск скачивает образ (~1 ГБ), дальше — из кеша.
Переменные: `ADMIN_USER` (по умолч. `admin`), `ADMIN_PASS` (`admin123`),
`DS_URL`, `UI_TEST_IMAGE`.

На локальном стенде (§0):
```bash
ADMIN_PASS=$(cat .dev_admin_pass) DS_URL=http://nginx bash ui_test.sh
```

Ожидаемый результат:
```
 Проверок пройдено: 82, провалено: 0, ошибок в браузере: 0
```
Код возврата `0` — можно выпускать; `1` — в выводе перечислены шаг и причина.

## Итог: чем пользоваться
| Инструмент | Уровень | Нужен живой стек | Скорость |
|---|---|---|---|
| `pytest` (server/tests) | Юнит: формулы, плейлисты, показы, дубли | Нет (БД замокана) | доли секунды |
| `pytest` (agent/tests) | Юнит: код агента (повторы, `active_until`, защита очистки диска, учёт показов) | Нет | доли секунды |
| `smoke_test.sh` | Сквозной: API + БД + цикл эфира, лента и закачка экрана | Да | секунды |
| `ui_test.sh` | Интерфейс: разделы, кнопки, плейлист «окно → показ → карточка → расписание» | Да | ~2–3 минуты |
| `dev_stand.sh` | Локальный стенд для всего вышеперечисленного | — | `up` ~минуты |

Полноценная проверка перед релизом — **все уровни**: сначала `pytest` сервера и
агента (быстро ловят регресс в логике), затем `smoke_test.sh` (живая система
отрабатывает цикл целиком), затем `ui_test.sh` (панель кликается и не сыплет
ошибками). Разработчику — всё это на локальном стенде `dev_stand.sh`. На боевом
сервере с живыми экранами запускайте **`smoke_test.sh`** (он создаёт только свои
`SMOKE_…` объекты на собственном тестовом экране); **`ui_test.sh` — не на боевом
сервере**, а на стенде или стеке без настоящих экранов (см. предупреждение в §3).
