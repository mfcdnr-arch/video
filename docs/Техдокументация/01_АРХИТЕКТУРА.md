## Компоненты

### Сервер (Docker Compose, 7 контейнеров)
| Контейнер | Роль |
|---|---|
| **ds_nginx** | Точка входа :80. Отдаёт веб-панель (статика), проксирует API и WebSocket, раздаёт медиафайлы мини-ПК. Единственный HTTP-порт наружу. |
| **ds_api** | FastAPI-приложение. Вся бизнес-логика: экраны, медиа, плейлисты, расписание, кампании, биллинг, модерация, пользователи, OTA. 17 роутеров в `server/routers/`. |
| **ds_postgres** | PostgreSQL 15. Все данные системы. Схема разворачивается миграциями `001`–`029` при первом старте. |
| **ds_redis** | Брокер и хранилище результатов для Celery. |
| **ds_celery** | Worker + Beat (флаг `-B`). Фоновые задачи: ночные бэкапы БД, бэкап медиа в MinIO, архивирование `play_log`, уведомления (MAX), пересчёт KPI. |
| **ds_minio** | S3-совместимое хранилище резервных копий медиа. |
| **ds_ntp** | chrony. Раздаёт точное время мини-ПК (udp/123), сам синхронизируется с ВНИИФТРИ/MSK-IX при наличии интернета. |

### Мини-ПК (агент, Astra Linux)
systemd-сервис `ds-agent` (Python). Модули: `ds_agent` (главный),
`ds_downloader` (скачивание медиа), `ds_player` (плеер + IPC-сокет),
`ds_sync` (синхронизация), `ds_heartbeat` (мониторинг), `ds_cleanup`
(очистка), `ds_ws_client` (WebSocket-команды), `ds_ota_updater` (самообновление).

## Потоки данных

**Публикация контента (оператор → экран):**
1. Оператор загружает ролик в панель → `api` кладёт файл в том `media_data`,
   запись в Postgres, статус модерации `pending`.
2. Модератор одобряет (38-ФЗ) → статус `approved`.
3. Оператор ставит ролик в плейлист и в расписание.
4. Агент опрашивает `api` (poll_interval 60 c), получает своё расписание,
   **скачивает** нужные файлы через nginx `/media/` (с докачкой по Range).
5. Плеер проигрывает по времени; синхронный старт по `sync_delay`.

**Команды в реальном времени (панель → экран):**
`api` пушит команду (перезапуск/перезагрузка) в `ds_ws_client` агента по
WebSocket (`/ws/`, `/api/ws/*`) — доставка мгновенная, без ожидания опроса.

**Мониторинг (экран → сервер):**
Агент шлёт heartbeat каждые ~30 c → `api` обновляет статус онлайн/офлайн,
свободное место, версию, играющий контент → видно на Дашборде.

**Точное время:** мини-ПК синхронизируются с `ds_ntp` (в изолированной сети —
единственный источник). Критично: расписание и учёт показов считаются по
московскому времени.

## Хранилище (Docker-тома)
| Том | Что хранит |
|---|---|
| `postgres_data` | База данных (все записи системы) |
| `media_data` | Загруженные медиафайлы (шарится: `api`, `celery` — rw; `nginx` — ro) |
| `minio_data` | Резервные копии медиа (S3) |
| `backup_data` | Ночные дампы БД |
| `agent_updates_data` | Пакеты OTA-обновления агентов |
| `nginx_logs` | Логи nginx |

> Тома переживают пересборку контейнеров. `docker compose down -v` их **удаляет**
> — только после бэкапа.

## Миграции БД
SQL-файлы `server/migrations/001`–`029`, применяются Postgres автоматически при
первом старте (список смонтирован в `docker-entrypoint-initdb.d` в
`docker-compose.yml`). На уже работающей БД недостающие миграции добивает
`migrate.sh` (вызывается из `install_server.sh` при обновлении).

> На момент актуальны `001`–`029` (026 — авто-снятие бегущей строки, 027 —
> архивы диагностики экранов, 028 — контроль подключения монитора к
> видеовыходу, 029 — раздел «Рекламодатели»: реквизиты, договоры, документы,
> компенсации, заявки). Новые миграции достаточно
> положить в `server/migrations/` — `migrate.sh`
> применит их идемпотентно; в `docker-compose.yml` их добавляют для применения на
> ЧИСТОЙ установке через initdb.

## Границы безопасности
- Наружу открыты только **:80** (nginx) и **:123/udp** (ntp).
- Postgres, Redis, MinIO, API **не** имеют проброса портов на хост — доступны
  только внутри сети Docker.
- Агенты аутентифицируются токеном устройства (заголовок `X-Token`).
- Пользователи панели — по логину/паролю, токен входа подписан `SECRET_KEY`.
- Секреты (`DB_PASSWORD`, `MINIO_PASSWORD`, `SECRET_KEY`) — в `.env` (права 600,
  в git не попадает).
- При первом входе панель **принудительно требует сменить** пароль admin по
  умолчанию (флаг `must_change_password`).

### Транспорт: HTTP без TLS — осознанное решение
Система работает по **HTTP** (без шифрования). Это принятое решение для
**изолированной indoor-сети**: сервер и мини-ПК в одном закрытом сегменте LAN,
наружу проброшены только порты 80 и 123/udp, внешнего доступа нет. В такой
конфигурации риск перехвата трафика низкий, и HTTP приемлем.

> **Когда включать HTTPS/TLS:** если панель/API станут доступны из внешней сети
> (интернет, общий Wi-Fi, доступ подрядчиков). Тогда логин и токены нельзя
> передавать в открытом виде. Шаги: сертификат (самоподписанный для внутренней
> сети или Let's Encrypt для публичного домена) → в `nginx.conf` добавить
> `listen 443 ssl` + редирект с 80 → пробросить 443 в `docker-compose.yml` →
> переустановить агенты с `https://…` (install.sh уже поддерживает https) →
> доверить сертификат на мини-ПК. Обязательна проверка на железе.
