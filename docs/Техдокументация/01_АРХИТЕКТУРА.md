## Компоненты

### Сервер (Docker Compose, 7 контейнеров)
| Контейнер | Роль |
|---|---|
| **ds_nginx** | Точка входа :80. Отдаёт веб-панель (статика), проксирует API и WebSocket, раздаёт медиафайлы — только после проверки в `api` (§ «Файлы медиатеки: только по входу»). Единственный HTTP-порт наружу. |
| **ds_api** | FastAPI-приложение. Вся бизнес-логика: экраны, медиа, плейлисты, расписание, кампании, биллинг, модерация, пользователи, OTA, «Эфир сети» и общий эфир. 20 роутеров в `server/routers/`. |
| **ds_postgres** | PostgreSQL 15. Все данные системы. Схема разворачивается миграциями `001`–`034` при первом старте. |
| **ds_redis** | Брокер и хранилище результатов для Celery. |
| **ds_celery** | Worker + Beat (флаг `-B`). Фоновые задачи: ночные бэкапы БД, бэкап медиа в MinIO, архивирование `play_log`, уведомления (MAX), пересчёт KPI, завершение общего эфира по сроку (`expire_broadcast`, раз в минуту), снятие бегущих строк по сроку (`expire_tickers`, раз в минуту). |
| **ds_minio** | S3-совместимое хранилище резервных копий медиа. |
| **ds_ntp** | chrony. Раздаёт точное время мини-ПК (udp/123), сам синхронизируется с ВНИИФТРИ/MSK-IX при наличии интернета. |

### Мини-ПК (агент, Astra Linux)
systemd-сервис `ds-agent` (Python). Модули: `ds_agent` (главный),
`ds_downloader` (скачивание медиа), `ds_player` (плеер + IPC-сокет),
`ds_sync` (синхронизация), `ds_heartbeat` (мониторинг), `ds_cleanup`
(очистка), `ds_ws_client` (WebSocket-команды), `ds_ota_updater` (самообновление).

## Потоки данных

**Публикация контента (оператор → экран):**
1. Оператор загружает ролик в панель → `api` кладёт файл в том `media_data`,
   запись в Postgres, статус модерации `pending`.
2. Модератор одобряет (38-ФЗ) → статус `approved`.
3. Оператор ставит ролик в плейлист и в расписание.
4. Агент опрашивает `api` (poll_interval 60 c), получает своё расписание и
   список файлов (`GET /api/files/list/{id}`) и **скачивает** их по
   `GET /api/files/download/{media_id}` с `X-Token` экрана: `api` проверяет токен
   и что ролик готов и одобрен, а сам файл отдаёт nginx (`X-Accel-Redirect`) — с
   докачкой по Range.
5. Плеер проигрывает по времени; синхронный старт по `sync_delay`.

**Команды в реальном времени (панель → экран):**
`api` пушит команду (перезапуск/перезагрузка) в `ds_ws_client` агента по
WebSocket (`/ws/`, `/api/ws/*`) — доставка мгновенная, без ожидания опроса.

**Мониторинг (экран → сервер):**
Агент шлёт heartbeat каждые ~30 c → `api` записывает время сигнала
(`screens.last_seen`), свободное место, версию, играющий ролик → видно на
Дашборде и в «Эфире сети». Агент 1.4.0 добавляет в heartbeat поле `ticker_state`
(какие бегущие строки у него бегут, раздел «Бегущая строка» ниже). Экран **«в сети»**, если последний сигнал не старше
5 минут (`screen_online.py`, одна константа `ONLINE_MINUTES`); правило считается
в SQL и отдаётся готовыми полями `online` и `offline_for_seconds` (`null` — ни
разу не выходил на связь), поэтому панель его не дублирует.

**Что идёт на экранах и общий эфир:** страница «Эфир сети» раз в 30 с читает
`GET /network/live` (запрос без ответа за 20 с обрывается — ошибка на странице,
автообновление не замирает) — одним запросом все экраны с тем, что идёт сейчас, до какого
часа, что дальше (или что пойдёт после общего эфира), каким роликом по сообщению
агента, и состоянием эфира (модули и API — раздел «Эфир сети и общий эфир» ниже).
Лента экрана отдаёт эфир первым приоритетом, но только если плейлисту эфира на
этом экране есть что играть, со сроком `active_until`; файлы плейлиста эфира
входят в список закачки экрана.

**Бегущая строка (срочные объявления):** строку знает сервер, а не только экран.
Лента экрана `GET /schedule/minipc/{id}` каждый раз отдаёт поле `tickers` — строки,
которые этому экрану положено показывать сейчас (срок, «все / группы / экраны» и
группа экрана решаются на момент запроса). Агент 1.4.0 крутит их по очереди, сам
снимает по сроку и сообщает в heartbeat `ticker_state`, какие у него бегут; по этим
отчётам панель считает «бежит на X из N». Запуск, правка и снятие доходят до экрана
за секунды: агент перечитывает ленту по команде `ticker_show` / `ticker_hide`
(для 1.4.0 это «обнови строки») и WS-сигналу `new_command`. Подробности — раздел
«Бегущая строка» ниже.

**Точное время:** мини-ПК синхронизируются с `ds_ntp` (в изолированной сети —
единственный источник). Критично: расписание и учёт показов считаются по
московскому времени.

## Хранилище (Docker-тома)
| Том | Что хранит |
|---|---|
| `postgres_data` | База данных (все записи системы) |
| `media_data` | Загруженные медиафайлы (шарится: `api`, `celery` — rw; `nginx` — ro) |
| `minio_data` | Резервные копии медиа (S3) |

> — только после бэкапа.

## Эфир сети и общий эфир

| Модуль | Роль |
|---|---|
| `routers/network.py` | `GET /network/live` — обзор сети для страницы «Эфир сети»: экраны (`venue_type`, `online`, `offline_for_seconds`), «сейчас / дальше / после эфира», «играет ролик», счётчики, состояние эфира; `GET /network/playlist/{id}/usage` — сколько слотов недельного шаблона занимает плейлист. SQL пакетный: показы, замены и решения читаются один раз на всех, «проигрываемые плейлисты» — один раз на тип площадки, недельный шаблон — одним запросом на всю сеть (`load_template_slots`) с раскладкой по экранам в Python (`placements_logic.slots_for_screen`: экран > группа > сеть), а не запросом на экран. |
| `network_live.py` | Чистая логика (без БД): что идёт на экране сейчас, до какого часа и что дальше (`screen_live`) поверх клеток `placements_logic.week_cells` — приоритеты те же, что у ленты экрана и «Расписания → По датам»; плейлист, которому на экране нечего играть (показ, замена на дату, слот шаблона), выпадает так же, как в ленте: пустой слот шаблона выбрасывается целиком, и идёт слот «весь день» или заглушки. |
| `routers/broadcast.py` | `GET /broadcast`; `POST /broadcast/on` с телом `{playlist_id, until_hour, on_date}` (`until_hour` — целое 1…24 позже текущего часа или `null` = «до отмены»; `on_date` — необязательная МСК-дата `ГГГГ-ММ-ДД`, на которую открыто окно в панели: при заданном `until_hour` и дате не равной сегодняшней по МСК — 400 «Время изменилось — проверьте час окончания», мусор вместо даты — 400, без `on_date` поведение прежнее; `playlist_id` — целое 1…2³¹−1, иначе 400; старый вызов `?playlist_id=N` без тела = «до отмены»); `POST /broadcast/off`. |
| `broadcast_rules.py` | Чистая логика: разбор часа окончания, «идёт ли эфир в момент `now`» (срок вышел — эфир уже выключен, не дожидаясь Celery). |
| `broadcast_store.py` | SQL: состояние эфира (`network_broadcast`, миграция 032 добавила `until_at`), включение / смена / выключение / истечение, записи журнала («Общий эфир включён / сменён / выключен / завершён по времени»). Включение и выключение читают строку под блокировкой: если срок прежнего эфира уже вышел, а Celery ещё не успел (до минуты), сначала пишется «завершён по времени» (от «система»), и «выключен» вторым не добавляется. Все читатели смотрят эфир через `get_broadcast`. |
| `screen_online.py` | Единое правило «в сети»: SQL-шаблоны `online_sql()` и `offline_for_sql()`. По ним считают список экранов, дашборд и его WS-пуш (`/ws/dashboard`), «Эфир сети», отчёты (сводка, неработающие экраны, простой, потери связи) и самодиагностика; `screens.status` для «в сети» не используется. |
| `playable_store.py` | Единое правило «ролик можно играть»: SQL-фрагмент `playable_sql()` (готов, одобрен модерацией, реклама алкоголя — только на площадке с алколицензией, срок показа не вышел; срок — наивное МСК, поэтому сравнивается с «сейчас» по Москве `NOW_MSK_SQL`, а не с `NOW()` БД в UTC — так же считают отчёт по срокам и плитка дашборда «истекает за 3 дня») и загрузчики `load_playable_items` (ролики плейлиста для ленты экрана) и `load_playable_by_venue` (обзор сети, флаги `GET /playlists`); тот же фрагмент берут часовой блок (`admin_panel.ad_sequence`) и слоты недельного шаблона в ленте экрана — ролик с вышедшим или ещё не начавшимся сроком не играет ни в одном источнике. Константы площадок — `LICENSED_VENUE`, `UNLICENSED_VENUE`, `DEFAULT_VENUE`. Симулятор проверяет срок на выбранную дату — у него свой вариант с той же частью про площадку (`venue_sql()`). |
| Celery `expire_broadcast` | Раз в минуту приводит строку эфира с вышедшим сроком в порядок и пишет в журнал «Общий эфир завершён по времени». |

Все отметки времени эфира и показов — наивное МСК, пишутся из Python (`now_msk`),
а не `NOW()` Postgres: контейнер БД живёт в UTC. Дополнительные поля API:
`GET /playlists` отдаёт `playable` (есть ролик, который может идти на экране:
готов, одобрен, срок не вышел) и `playable_unlicensed` (то же для площадки без
алколицензии); строки `GET /network/live` содержат `venue_type` — по ним окно
включения эфира заранее считает экраны, где плейлисту нечего играть.

## Бегущая строка

| Модуль | Роль |
|---|---|
| `routers/ticker.py` | `GET /tickers` — список живых строк прежнего вида (`id`, `message`, `color`, `speed`, `is_all`) плюс `target`, `until_at`, `started_at`, `started_by`; `GET /tickers/overview` — всё для страницы одним ответом: строки (с `screens_total`, `remaining_seconds` и подтверждением `confirm` = «бежит на X из N» + список проблемных экранов с причинами; у каждого — `screen_id`, имена экранов могут повторяться), экраны (`live_count` — сколько живых строк у экрана), группы, шаблоны, `generated_at`; `POST /tickers` — запустить (тело `{message, color, speed, target: all\|groups\|screens, group_ids \| screen_ids, term: {kind: cancel\|hour\|minutes, hour \| minutes, on_date}}`; прежнее тело `{message, is_all, screen_ids, duration}` тоже принимается); `PUT /tickers/{id}` — поправить (нет `term` — прежний момент окончания; нет `target` — 400 «Укажите, где показывать строку»; нет строки или срок вышел — 404); `DELETE /tickers/{id}` — снять; `GET/POST /ticker-templates`, `PUT/DELETE /ticker-templates/{id}` — шаблоны. Смотреть — любой вошедший в панель (кроме рекламодателя), менять — `require_write`. Неверное тело — 400 с русским пояснением. После каждого изменения экранам, которых строка касалась до и касается после, ставится команда, а подключённым по WebSocket уходит `new_command`. |
| `ticker_rules.py` | Чистая логика (без БД): разбор тела и срока (`parse_ticker_body`, `parse_term`: «до снятия», «до ЧЧ:00» с защитой `on_date` от смены часа, «на N минут» от 1 до 1440 — может перейти через полночь; текст 1–200 знаков (`\r \n \t \v \f`, NEL, U+2028/2029 → пробел; NUL, прочие управляющие символы и одинокие суррогаты — 400), цвет `#RRGGBB`, скорость `slow \| medium \| fast`), «где» на момент показа (`resolve_screens`), строки экрана в порядке запуска (`tickers_for_screen`), причины «не бежит» (`screen_reason`: не в сети → старый агент → остановлен («Стоп») → экран выключен по расписанию питания → бежит → ждём подтверждения (90 с от запуска или правки) → не подтвердил) и итог `summarize`. Подтверждают агенты от `CONFIRM_VERSION` = 1.4.0. |
| `ticker_store.py` | SQL: запуск / правка / снятие / истечение (`create`, `update`, `remove`, `expire_due`), строки экрана для ленты (`for_screen`), отчёт экрана (`record_report`), команды старым агентам (`notify_screens`), шаблоны, записи журнала `audit_log` с `event_type='ticker'` («Бегущая строка запущена / изменена / снята / снята по сроку»). `commit` делает вызывающий роутер. Все моменты — наивное МСК из Python. |
| Celery `expire_tickers` | Раз в минуту убирает строки с вышедшим сроком и пишет в журнал «Бегущая строка снята по сроку» (от «система», по разу на строку). Строка исчезает с экрана и без неё: агент снимает её сам по сроку из ленты; задача лишь приводит БД и журнал в порядок. Экранам со старым агентом ставится команда об оставшейся самой новой строке или `ticker_hide`. |
| Лента экрана | Поле `tickers`: `[{id, message, color, speed, until_at}]`. Ключ есть всегда, кроме сбоя чтения строк: без ключа агент 1.4.0 оставляет текущий список (пустой список означал бы «строк нет» и снял бы живые объявления из-за временного сбоя БД). |
| Heartbeat | Поле `ticker_state` = `{ids, stopped, screen_off}` пишется в `screens.ticker_ids`, `ticker_stopped`, `ticker_screen_off`; `NULL` — агент до 1.4.0 такого отчёта не присылает («старый агент — без подтверждения»). Запись отчёта идёт отдельным шагом после commit сигнала: сбой отчёта не стоит экрану ни `last_seen`, ни ответа. Агент включает в `ids` только строки, чей кадр дошёл до mpv не позже 2 с назад. Тем же heartbeat сервер будит подключённый по WS экран (`new_command`), если в его очереди есть команда старше 10 с (один `COUNT`; сбой проверки heartbeat не роняет). |

Таблицы (миграция 034): `tickers` (+ `until_at`, `target`, `started_at/by`, `changed_at/by`; `until_at IS NULL` —
«до снятия»), `ticker_screens` (экраны строки, миграция 002), `ticker_groups` (группы строки; состав группы смотрится в
момент показа), `ticker_templates` (шаблоны: текст, вид, срок; три стартовых вставляются, только если таблица пуста),
`screens.ticker_ids / ticker_stopped / ticker_screen_off` (последний отчёт агента). Старые строки миграция переносит: неактивные и истёкшие удаляет,
остальным ставит цель (`is_all` → `all` или `screens`), срок в МСК и время запуска.

**Старые агенты (< 1.4.0)** по-прежнему получают строку командами `ticker_show` / `ticker_hide` —
одну на экран, без переживания перезагрузки. Две поправки: «Стоп» шлёт `ticker_hide` только этому экрану
(и только если у экрана есть живые строки), а при снятии одной из нескольких строк экрану заново ставится
`ticker_show` самой новой из оставшихся. «Стоп» больше не снимает строки нигде: на остановленном экране строка
не видна, после «Показ» бежит дальше, если срок не вышел; смена плейлиста (слот, показ, общий эфир) строки не трогает.
Команды строки — **состояние, а не события**: перед каждой новой `ticker_show` / `ticker_hide` экрана его ожидающие `ticker_*`
гасятся (`executed_at`), так что в очереди остаётся одна актуальная команда (агент < 1.4.0 по WS берёт одну команду за
сигнал, и устаревшая съела бы сигнал следующего запуска); прочие команды не затрагиваются. У Celery `expire_tickers`
WS-сигнала нет — такую команду подгонит heartbeat (см. выше).

Все моменты строк — наивное МСК из Python (`now_msk`), не `NOW()` Postgres.

## Миграции БД
SQL-файлы `server/migrations/001`–`034`, применяются Postgres автоматически при
первом старте (список смонтирован в `docker-entrypoint-initdb.d` в
`docker-compose.yml`). На уже работающей БД недостающие миграции добивает
`migrate.sh` (вызывается из `install_server.sh` при обновлении).

Учёт применённых файлов — таблица `schema_migrations`; initdb в неё не пишет.
Поэтому первый `migrate.sh` после свежей установки делает **baseline**: если
учёта ещё не было, схема уже есть, а экранов нет, файлы из списка initdb
записываются как применённые без повторного запуска («Учёт миграций начат…»).
Файл, которого нет в списке initdb, применяется обычным порядком. На живой базе
без учёта (экраны есть) baseline не делается — применяются все миграции, как
раньше. Готовность `migrate.sh` и `install_server.sh` ждут по TCP: пока идут
скрипты initdb, временный Postgres слушает только сокет, и baseline посреди
initdb записал бы ещё не применённые файлы.

Сиды пишутся так, чтобы повтор миграции не плодил строки: `ON CONFLICT` — только
там, где есть уникальный ключ, иначе `INSERT … SELECT … WHERE NOT EXISTS`.

> Последние: 026 — `screens.last_playlist_id` (раньше по нему снималась бегущая
> строка, теперь значение только справочное), 027 — архивы диагностики
> экранов, 028 — контроль подключения монитора к видеовыходу, 029 — раздел
> «Рекламодатели»: реквизиты, договоры, документы, компенсации, заявки, 030 —
> госорганы как владельцы контента без биллинга, 031 — показы по датам, 032 —
> срок общего эфира («до ЧЧ:00»), 033 — одно имя — одна группа экранов: дубли
> `sync_groups` по имени сливаются в группу с минимальным id (экраны, групповые
> слоты, замены на дату и кампании переезжают на неё; при совпадении слота или
> замены остаётся строка оставшейся группы), затем уникальный индекс
> `uq_sync_groups_name`; `POST /groups` на занятое имя отвечает 409, 034 — бегущая
> строка: срок и «где» (`tickers`), группы строки (`ticker_groups`), шаблоны
> (`ticker_templates`), отчёт агента о строках в `screens`. Новые миграции достаточно
> положить в `server/migrations/` — `migrate.sh`
> применит их идемпотентно; в `docker-compose.yml` их добавляют для применения на
> ЧИСТОЙ установке через initdb.

## Файлы медиатеки: только по входу
Ролики, баннеры, сканы из папки «Документы» и миниатюры отдаются только тем, кто
вошёл, — номера роликов идут подряд, и открытая ссылка позволяла выкачать всю
медиатеку перебором (вместе с роликами на модерации и отклонёнными). Правило
одно — `server/media_access.py`:

| Кто | Чем подтверждает | Что получает |
|---|---|---|
| Агент мини-ПК (любая версия) | `X-Token` экрана | `GET /api/files/download/{id}` — только готовый одобренный ролик, остальное «не найдено» (404) |
| Пользователь панели (кроме роли «рекламодатель») | JWT в `Authorization` или cookie `ds_media` | любой файл, миниатюра, `/media/<имя>` |
| Без входа, поддельный или истёкший вход | — | 401 на любой номер (раньше 404) |
| Рекламодатель, заблокированный | — | 403 |

Как устроена отдача:
- **`GET /api/files/download/{id}`** (агент, кнопка «Скачать») — `api` проверяет
  доступ и отвечает пустым телом с `X-Accel-Redirect: /_media_files/<имя>`; файл
  выдаёт nginx из internal-локации (снаружи она не открывается) — с Range,
  `sendfile` и `limit_rate`. Так у агента работает докачка: `FileResponse`
  starlette 0.35 Range не умеет. Признак «за nginx» — заголовок `X-DS-Accel: 1`,
  его ставит только nginx; без него (прямо в `api`) файл отдаётся целиком.
- **`/media/<имя>`** (просмотр ролика в панели, `<video>` с перемоткой) — nginx
  перед отдачей спрашивает `GET /files/auth` (`auth_request`): 204 — отдать,
  401/403 — тот же код клиенту. Токен экрана сюда не годится.
- **`GET /api/media/{id}/thumbnail`** — миниатюры, только вход в панель.

`<img>`, `<video>` и ссылка «Скачать» заголовок с токеном не несут, а видео в сотни
мегабайт через blob не скачать. Поэтому панель при старте, перед просмотром и
скачиванием зовёт `POST /api/session/media`, и сервер ставит **cookie `ds_media`**:
httpOnly (скрипт её не видит), `SameSite=Strict` (чужой сайт её не пошлёт), живёт
до конца текущего входа (exp JWT), подписана **отдельным ключом** из `SECRET_KEY`
— как токен входа в API она не годится, токен входа в cookie тоже. В адрес она не
попадает, значит, не оседает в логах nginx. Пользователь проверяется в БД на
каждый запрос — блокировка действует сразу. Выход из панели снимает cookie
(`DELETE /api/session/media`).

## Роль «рекламодатель»: два независимых рубежа
Учётка с ролью `advertiser` привязана к записи рекламодателя
(`users.advertiser_id`, заводится автоматически при создании пользователя).
Ограничение доступа сделано **на сервере в двух местах**, потому что скрытие
пунктов меню в панели защитой не является — API можно позвать напрямую:

1. **Middleware `advertiser_guard`** (`server/main.py`) — белый список путей
   (`deps._ADV_ALLOWED`), всё остальное 403. Принцип «запрещено по умолчанию»:
   один забытый эндпоинт не превращается в утечку чужого эфира и счетов.
2. **Зависимость `advertiser_scope`** (`server/deps.py`) — id кабинета в пути
   обязан совпадать с привязкой учётки, иначе 403. Перебором номеров чужую
   карточку не открыть.

WebSocket-соединения middleware не проходят, поэтому дашборд-поток
(`/ws/dashboard`) отсекает эту роль отдельной проверкой в
`routers/websockets.py`. Изоляция закреплена E2E-прогоном (`ui_test.sh`).

## Границы безопасности
- Наружу открыты только **:80** (nginx) и **:123/udp** (ntp).
- Postgres, Redis, MinIO, API **не** имеют проброса портов на хост — доступны
  только внутри сети Docker.
- Агенты аутентифицируются токеном устройства (заголовок `X-Token`).
- Пользователи панели — по логину/паролю, токен входа подписан `SECRET_KEY`.
- Файлы медиатеки, бэкапы БД и архивы диагностики без входа не отдаются (401),
  см. «Файлы медиатеки: только по входу».
- Секреты (`DB_PASSWORD`, `MINIO_PASSWORD`, `SECRET_KEY`) — в `.env` (права 600,
  в git не попадает).
- При первом входе панель **принудительно требует сменить** пароль admin по
  умолчанию (флаг `must_change_password`).

### Транспорт: HTTP без TLS — осознанное решение
Система работает по **HTTP** (без шифрования). Это принятое решение для
**изолированной indoor-сети**: сервер и мини-ПК в одном закрытом сегменте LAN,
наружу проброшены только порты 80 и 123/udp, внешнего доступа нет. В такой
конфигурации риск перехвата трафика низкий, и HTTP приемлем.

> **Когда включать HTTPS/TLS:** если панель/API станут доступны из внешней сети
> (интернет, общий Wi-Fi, доступ подрядчиков). Тогда логин и токены нельзя
> передавать в открытом виде. Шаги: сертификат (самоподписанный для внутренней
> сети или Let's Encrypt для публичного домена) → в `nginx.conf` добавить
> `listen 443 ssl` + редирект с 80 → пробросить 443 в `docker-compose.yml` →
> переустановить агенты с `https://…` (install.sh уже поддерживает https) →
> доверить сертификат на мини-ПК. Обязательна проверка на железе.
