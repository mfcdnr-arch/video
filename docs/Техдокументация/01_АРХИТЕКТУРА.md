## Компоненты

### Сервер (Docker Compose, 7 контейнеров)
| Контейнер | Роль |
|---|---|
| **ds_nginx** | Точка входа :80. Отдаёт веб-панель (статика), проксирует API и WebSocket, раздаёт медиафайлы мини-ПК. Единственный HTTP-порт наружу. |
| **ds_api** | FastAPI-приложение. Вся бизнес-логика: экраны, медиа, плейлисты, расписание, кампании, биллинг, модерация, пользователи, OTA, «Эфир сети» и общий эфир. 20 роутеров в `server/routers/`. |
| **ds_postgres** | PostgreSQL 15. Все данные системы. Схема разворачивается миграциями `001`–`032` при первом старте. |
| **ds_redis** | Брокер и хранилище результатов для Celery. |
| **ds_celery** | Worker + Beat (флаг `-B`). Фоновые задачи: ночные бэкапы БД, бэкап медиа в MinIO, архивирование `play_log`, уведомления (MAX), пересчёт KPI, завершение общего эфира по сроку (`expire_broadcast`, раз в минуту). |
| **ds_minio** | S3-совместимое хранилище резервных копий медиа. |
| **ds_ntp** | chrony. Раздаёт точное время мини-ПК (udp/123), сам синхронизируется с ВНИИФТРИ/MSK-IX при наличии интернета. |

### Мини-ПК (агент, Astra Linux)
systemd-сервис `ds-agent` (Python). Модули: `ds_agent` (главный),
`ds_downloader` (скачивание медиа), `ds_player` (плеер + IPC-сокет),
`ds_sync` (синхронизация), `ds_heartbeat` (мониторинг), `ds_cleanup`
(очистка), `ds_ws_client` (WebSocket-команды), `ds_ota_updater` (самообновление).

## Потоки данных

**Публикация контента (оператор → экран):**
1. Оператор загружает ролик в панель → `api` кладёт файл в том `media_data`,
   запись в Postgres, статус модерации `pending`.
2. Модератор одобряет (38-ФЗ) → статус `approved`.
3. Оператор ставит ролик в плейлист и в расписание.
4. Агент опрашивает `api` (poll_interval 60 c), получает своё расписание,
   **скачивает** нужные файлы через nginx `/media/` (с докачкой по Range).
5. Плеер проигрывает по времени; синхронный старт по `sync_delay`.

**Команды в реальном времени (панель → экран):**
`api` пушит команду (перезапуск/перезагрузка) в `ds_ws_client` агента по
WebSocket (`/ws/`, `/api/ws/*`) — доставка мгновенная, без ожидания опроса.

**Мониторинг (экран → сервер):**
Агент шлёт heartbeat каждые ~30 c → `api` записывает время сигнала
(`screens.last_seen`), свободное место, версию, играющий ролик → видно на
Дашборде и в «Эфире сети». Экран **«в сети»**, если последний сигнал не старше
5 минут (`screen_online.py`, одна константа `ONLINE_MINUTES`); правило считается
в SQL и отдаётся готовыми полями `online` и `offline_for_seconds` (`null` — ни
разу не выходил на связь), поэтому панель его не дублирует.

**Что идёт на экранах и общий эфир:** страница «Эфир сети» раз в 30 с читает
`GET /network/live` — одним запросом все экраны с тем, что идёт сейчас, до какого
часа, что дальше (или что пойдёт после общего эфира), каким роликом по сообщению
агента, и состоянием эфира (модули и API — раздел «Эфир сети и общий эфир» ниже).
Лента экрана отдаёт эфир первым приоритетом, но только если плейлисту эфира на
этом экране есть что играть, со сроком `active_until`; файлы плейлиста эфира
входят в список закачки экрана.

**Точное время:** мини-ПК синхронизируются с `ds_ntp` (в изолированной сети —
единственный источник). Критично: расписание и учёт показов считаются по
московскому времени.

## Хранилище (Docker-тома)
| Том | Что хранит |
|---|---|
| `postgres_data` | База данных (все записи системы) |
| `media_data` | Загруженные медиафайлы (шарится: `api`, `celery` — rw; `nginx` — ro) |
| `minio_data` | Резервные копии медиа (S3) |

## Эфир сети и общий эфир

| Модуль | Роль |
|---|---|
| `routers/network.py` | `GET /network/live` — обзор сети для страницы «Эфир сети»: экраны (`venue_type`, `online`, `offline_for_seconds`), «сейчас / дальше / после эфира», «играет ролик», счётчики, состояние эфира; `GET /network/playlist/{id}/usage` — сколько слотов недельного шаблона занимает плейлист. SQL пакетный: показы, замены и решения читаются один раз на всех, «проигрываемые плейлисты» — один раз на тип площадки, недельный шаблон — одним запросом на всю сеть (`load_template_slots`) с раскладкой по экранам в Python (`placements_logic.slots_for_screen`: экран > группа > сеть), а не запросом на экран. |
| `network_live.py` | Чистая логика (без БД): что идёт на экране сейчас, до какого часа и что дальше (`screen_live`) поверх клеток `placements_logic.week_cells` — приоритеты те же, что у ленты экрана и «Расписания → По датам»; плейлист, которому на экране нечего играть (показ, замена на дату, слот шаблона), выпадает так же, как в ленте: пустой слот шаблона выбрасывается целиком, и идёт слот «весь день» или заглушки. |
| `routers/broadcast.py` | `GET /broadcast`; `POST /broadcast/on` с телом `{playlist_id, until_hour, on_date}` (`until_hour` — целое 1…24 позже текущего часа или `null` = «до отмены»; `on_date` — необязательная МСК-дата `ГГГГ-ММ-ДД`, на которую открыто окно в панели: при заданном `until_hour` и дате не равной сегодняшней по МСК — 400 «Время изменилось — проверьте час окончания», мусор вместо даты — 400, без `on_date` поведение прежнее; `playlist_id` — целое 1…2³¹−1, иначе 400; старый вызов `?playlist_id=N` без тела = «до отмены»); `POST /broadcast/off`. |
| `broadcast_rules.py` | Чистая логика: разбор часа окончания, «идёт ли эфир в момент `now`» (срок вышел — эфир уже выключен, не дожидаясь Celery). |
| `broadcast_store.py` | SQL: состояние эфира (`network_broadcast`, миграция 032 добавила `until_at`), включение / смена / выключение / истечение, записи журнала («Общий эфир включён / сменён / выключен / завершён по времени»). Включение и выключение читают строку под блокировкой: если срок прежнего эфира уже вышел, а Celery ещё не успел (до минуты), сначала пишется «завершён по времени» (от «система»), и «выключен» вторым не добавляется. Все читатели смотрят эфир через `get_broadcast`. |
| `screen_online.py` | Единое правило «в сети»: SQL-шаблоны `online_sql()` и `offline_for_sql()`. По ним считают список экранов, дашборд и его WS-пуш (`/ws/dashboard`), «Эфир сети», отчёты (сводка, неработающие экраны, простой, потери связи) и самодиагностика; `screens.status` для «в сети» не используется. |
| `playable_store.py` | Единое правило «ролик можно играть»: SQL-фрагмент `playable_sql()` (готов, одобрен модерацией, реклама алкоголя — только на площадке с алколицензией, срок показа не вышел) и загрузчики `load_playable_items` (ролики плейлиста для ленты экрана) и `load_playable_by_venue` (обзор сети, флаги `GET /playlists`); тот же фрагмент берёт часовой блок (`admin_panel.ad_sequence`). Константы площадок — `LICENSED_VENUE`, `UNLICENSED_VENUE`, `DEFAULT_VENUE`. Симулятор проверяет срок на выбранную дату — у него свой вариант с той же частью про площадку (`venue_sql()`). |
| Celery `expire_broadcast` | Раз в минуту приводит строку эфира с вышедшим сроком в порядок и пишет в журнал «Общий эфир завершён по времени». |

Все отметки времени эфира и показов — наивное МСК, пишутся из Python (`now_msk`),
а не `NOW()` Postgres: контейнер БД живёт в UTC. Дополнительные поля API:
`GET /playlists` отдаёт `playable` (есть ролик, который может идти на экране:
готов, одобрен, срок не вышел) и `playable_unlicensed` (то же для площадки без
алколицензии); строки `GET /network/live` содержат `venue_type` — по ним окно
включения эфира заранее считает экраны, где плейлисту нечего играть.

## Миграции БД
SQL-файлы `server/migrations/001`–`032`, применяются Postgres автоматически при
первом старте (список смонтирован в `docker-entrypoint-initdb.d` в
`docker-compose.yml`). На уже работающей БД недостающие миграции добивает
`migrate.sh` (вызывается из `install_server.sh` при обновлении).

> Последние: 026 — авто-снятие бегущей строки, 027 — архивы диагностики
> экранов, 028 — контроль подключения монитора к видеовыходу, 029 — раздел
> «Рекламодатели»: реквизиты, договоры, документы, компенсации, заявки, 030 —
> госорганы как владельцы контента без биллинга, 031 — показы по датам, 032 —
> срок общего эфира («до ЧЧ:00»). Новые миграции достаточно
> положить в `server/migrations/` — `migrate.sh`
> применит их идемпотентно; в `docker-compose.yml` их добавляют для применения на
> ЧИСТОЙ установке через initdb.

## Роль «рекламодатель»: два независимых рубежа
Учётка с ролью `advertiser` привязана к записи рекламодателя
(`users.advertiser_id`, заводится автоматически при создании пользователя).
Ограничение доступа сделано **на сервере в двух местах**, потому что скрытие
пунктов меню в панели защитой не является — API можно позвать напрямую:

1. **Middleware `advertiser_guard`** (`server/main.py`) — белый список путей
   (`deps._ADV_ALLOWED`), всё остальное 403. Принцип «запрещено по умолчанию»:
   один забытый эндпоинт не превращается в утечку чужого эфира и счетов.
2. **Зависимость `advertiser_scope`** (`server/deps.py`) — id кабинета в пути
   обязан совпадать с привязкой учётки, иначе 403. Перебором номеров чужую
   карточку не открыть.

WebSocket-соединения middleware не проходят, поэтому дашборд-поток
(`/ws/dashboard`) отсекает эту роль отдельной проверкой в
`routers/websockets.py`. Изоляция закреплена E2E-прогоном (`ui_test.sh`).

## Границы безопасности
- Наружу открыты только **:80** (nginx) и **:123/udp** (ntp).
- Postgres, Redis, MinIO, API **не** имеют проброса портов на хост — доступны
  только внутри сети Docker.
- Агенты аутентифицируются токеном устройства (заголовок `X-Token`).
- Пользователи панели — по логину/паролю, токен входа подписан `SECRET_KEY`.
- Секреты (`DB_PASSWORD`, `MINIO_PASSWORD`, `SECRET_KEY`) — в `.env` (права 600,
  в git не попадает).
- При первом входе панель **принудительно требует сменить** пароль admin по
  умолчанию (флаг `must_change_password`).

### Транспорт: HTTP без TLS — осознанное решение
Система работает по **HTTP** (без шифрования). Это принятое решение для
**изолированной indoor-сети**: сервер и мини-ПК в одном закрытом сегменте LAN,
наружу проброшены только порты 80 и 123/udp, внешнего доступа нет. В такой
конфигурации риск перехвата трафика низкий, и HTTP приемлем.

> **Когда включать HTTPS/TLS:** если панель/API станут доступны из внешней сети
> (интернет, общий Wi-Fi, доступ подрядчиков). Тогда логин и токены нельзя
> передавать в открытом виде. Шаги: сертификат (самоподписанный для внутренней
> сети или Let's Encrypt для публичного домена) → в `nginx.conf` добавить
> `listen 443 ssl` + редирект с 80 → пробросить 443 в `docker-compose.yml` →
> переустановить агенты с `https://…` (install.sh уже поддерживает https) →
> доверить сертификат на мини-ПК. Обязательна проверка на железе.
