# 03. Runbook — реагирование на инциденты

Пошаговые действия при отказах. Все команды выполняются на **сервере** из каталога
проекта, если не указано иное. Имена контейнеров: `ds_postgres`, `ds_redis`,
`ds_minio`, `ds_api`, `ds_celery`, `ds_nginx`, `ds_ntp`.

## 0. Первичная диагностика (всегда с этого)

**Быстрый путь — самодиагностика.** Если панель открывается: **Настройки →
Диагностика сервера → «Запустить проверку»** — каждая служба со статусом и
подсказкой, что сделать. Если панель НЕ открывается — на хосте:
```bash
cd Video_miniPC_v16.2_modular
bash selfheal.sh --dry-run   # покажет проблемы и что бы починил
bash selfheal.sh             # починит типовое сам (упавшие контейнеры,
                             # рестарт-цикл ntp, «чёрную панель» из-за nginx)
```
`selfheal.sh` можно повесить в cron раз в 5 минут — команда установки в шапке
самого скрипта.

**Ручной путь**, если нужно смотреть глубже:
```bash
docker compose ps                    # кто НЕ running / unhealthy
curl -s http://localhost/health      # API отвечает?
docker stats --no-stream             # не упёрлись ли в память/CPU
df -h                                # не кончилось ли место на диске
```
Определите слой: контейнеры → API → БД/хранилище → сеть/агенты.

## 1. Не открывается панель / API не отвечает

**Симптом:** браузер не грузит панель, `curl /health` не 200.
Либо: страница открывается, но **вся чёрная/пустая** (тёмный фон без формы
логина и меню) — статику nginx отдаёт, а API лежит (`/health` → 502), и
JS-панель не может отрисоваться. Диагноз и лечение те же.

1. `docker compose ps` — какой контейнер лежит.
2. Если лежит **nginx**: `docker compose logs --tail=50 nginx`. Частое — ошибка в
   `nginx.conf`. Проверить и перезапустить: `docker compose restart nginx`.
3. Если лежит **api**: `docker compose logs --tail=100 api`.
   - `api` не поднимется, пока не healthy `postgres` и `redis` — см. §2, §4.
   - После починки зависимостей: `docker compose up -d api`.
4. Если все `running`, но `/health` не 200 — API завис:
   `docker compose restart api`, затем следить `docker compose logs -f api`.
5. Если `api` — `Up (healthy)` и в его логах `GET /health … 200 OK`, а снаружи
   всё равно **502** — nginx держит устаревший IP контейнера `api` (nginx
   резолвит имя апстрима один раз при старте; если `api` пересоздавался, а
   nginx нет — прокси бьёт в пустоту). Признак: аптайм nginx БОЛЬШЕ аптайма
   api в `docker ps`. Лечение: `docker restart ds_nginx`.

## 2. Упал PostgreSQL (ds_postgres)

**Симптом:** `api` в логах пишет ошибки соединения с БД; панель не работает.

1. Статус и логи:
   ```bash
   docker compose ps postgres
   docker compose logs --tail=100 postgres
   docker exec ds_postgres pg_isready -U display_user -d display_system
   ```
2. Если контейнер упал/рестартится — обычно **нехватка места** (см. §6) или
   повреждение. Освободите диск, затем `docker compose up -d postgres`.
3. Дождитесь healthy (`docker compose ps`), поднимите зависящие:
   `docker compose up -d api celery`.
4. **Если БД повреждена** — восстановление из ночного дампа:
   см. [../RESTORE_GUIDE.md](../RESTORE_GUIDE.md). Дампы — в томе `backup_data`.
5. Если postgres healthy, а api пишет `password authentication failed for user
   "display_user"` (вход в панель отвечает 500) — рассинхрон `.env` с томом БД
   (обычно после обновления с потерей старого `.env`). Лечение — в
   [08_ОБНОВЛЕНИЕ_СЕРВЕРА, врезка «Если .env потерялся»](../Инструкции/08_ОБНОВЛЕНИЕ_СЕРВЕРА.md).
6. Проверка после подъёма: `bash smoke_test.sh`.

> ⚠️ Никогда не запускайте `docker compose down -v` для «перезапуска» — флаг `-v`
> сотрёт том `postgres_data` (всю базу).

---

## 3. Упал MinIO (ds_minio)

**Влияние:** ограничено — MinIO хранит **резервные копии медиа**. На показ и
работу панели прямо **не влияет**; ломается только бэкап медиа.

1. `docker compose logs --tail=50 minio`; частое — нет места (см. §6).
2. `docker compose up -d minio`.
3. Проверить прохождение бэкапа медиа: `docker compose logs celery | grep -i minio`.
4. Если MinIO долго лежал — следующий ночной бэкап Celery нагонит пропуск;
   форсировать вручную можно из панели (раздел бэкапов).

---

## 4. Упал Redis (ds_redis)

**Влияние:** брокер Celery. Панель и показ работают; **не выполняются фоновые
задачи** (бэкапы, уведомления, архивирование, KPI).

1. `docker compose logs --tail=50 redis`; `docker exec ds_redis redis-cli ping` → `PONG`.
2. `docker compose up -d redis`, затем `docker compose restart celery`.
3. Убедиться, что worker поднялся: `docker compose logs --tail=30 celery`.

---

## 5. Часть экранов офлайн (например, 30%)

**Симптом:** на Дашборде группа экранов «офлайн». Экран считается «в сети», если
его последний heartbeat пришёл не позже **5 минут** назад (одно правило для всей
панели); дальше он «не в сети X мин», а ни разу не выходивший на связь —
«ни разу не выходил на связь». Раздел «Эфир сети» показывает ту же картину по
всем экранам разом.

Сначала определите масштаб — **сеть или сами мини-ПК**:
1. Офлайн **все разом** → проблема на **сервере/сети**, не на экранах:
   - Проверьте, что `api`/`nginx` живы (§1) и порт 80 доступен из сегмента
     мини-ПК.
   - Проверьте питание/линк сетевого коммутатора этого сегмента.
2. Офлайн **часть/точечно** → проблема на конкретных мини-ПК:
   - С сервера: доступен ли мини-ПК — `ping <IP_мини_ПК>`.
   - На мини-ПК (по SSH/локально):
     ```bash
     systemctl status ds-agent
     journalctl -u ds-agent -n 50 --no-pager
     curl -sf http://10.0.119.100/health     # видит ли агент сервер
     ```
   - Перезапуск агента: `sudo systemctl restart ds-agent` (или команда
     «перезапуск» из панели, если WebSocket ещё жив).
3. `«Invalid device token»` в логах агента → токен в `/etc/ds-agent/config.ini`
   не совпадает с токеном экрана в панели. Синхронизировать.
4. Массовый офлайн после OTA-обновления агента → см. §8.

## 6. Кончается место на диске

**Симптом:** контейнеры рестартятся/падают (Postgres, MinIO), ошибки записи.

1. `df -h` и что занимает: `docker system df -v`.
2. Быстро освободить:
   ```bash
   docker image prune -f            # висячие образы
   docker builder prune -f          # кэш сборки
   ```
3. Ротация логов контейнеров: используйте `docker-compose.prod.yml` (лимиты
   `max-size`/`max-file`) — см. [../Инструкции/01_УСТАНОВКА_СЕРВЕР.md](../Инструкции/01_УСТАНОВКА_СЕРВЕР.md).
4. Старые дампы БД в томе `backup_data` — регулируются `BACKUP_KEEP` в `.env`.
5. Медиа: удалите неиспользуемые ролики из панели (Медиатека).
6. После освобождения места: `docker compose up -d` и проверьте `docker compose ps`.

## 7. Экран онлайн, но ничего не играет / чёрный экран

**Симптом:** мини-ПК онлайн (heartbeat идёт), но контента нет.

Сначала в панели (раздел «Экраны»): красный бейдж **📺** и строка «Монитор
отключён от видеовыхода» означают, что дело не в контенте — мини-ПК играет,
но монитор не подключён к HDMI/DisplayPort (или обесточен). Тогда идти нужно
к самому монитору и кабелю, а не к агенту. Серый бейдж = состояние
неизвестно (агент старее 1.2.0 либо драйвер не сообщает статус).

На мини-ПК:
1. Плеер запущен? `pgrep -a mpv` (или процесс плеера).
2. Логи агента: `tail -n 80 /var/log/ds-agent/ds-agent.log`.
3. Скачались ли файлы? `ls -la /opt/ds-agent/media`.
   - Пусто/битые → проверьте, что сервер отдаёт файлы этому экрану (агент качает
     по своему токену, `/media/` для него закрыт):
     ```bash
     T=$(sudo awk -F' *= *' '/^token/{print $2}' /etc/ds-agent/config.ini)
     curl -s -H "X-Token: $T" http://10.0.119.100/api/files/list/$(cat /etc/ds-agent/screen_id)   # что экран должен скачать
     curl -I -H "X-Token: $T" http://10.0.119.100/api/files/download/<media_id>                     # 200 — отдаётся
     ```
     401 — токен в `config.ini` не совпадает с токеном экрана в панели; 404 —
     ролик не одобрен (`pending` / отклонён), удалён или файла нет на диске сервера.
4. Есть ли расписание на **сейчас**? В панели: назначен ли плейлист на этот
   экран/группу/сеть, не истёк ли срок «с/по», одобрены ли ролики (не `pending`).
   Быстрее всего — раздел «Эфир сети»: в строке экрана видно, что и по какому
   источнику должно идти (расписание / показ / общий эфир) и какой ролик экран
   сообщил последним. Пометка «общий эфир на этом экране не идёт — нечего
   играть» значит, что в плейлисте эфира нет роликов, допустимых для этого экрана
   (не одобрены, вышел срок, реклама алкоголя без алколицензии).
5. Время мини-ПК: `chronyc tracking` — при большом смещении слот расписания «не
   совпадёт». Починка времени — §9.
6. Перезапуск: `sudo systemctl restart ds-agent`.

> Полноэкранный запуск mpv на реальном железе мини-ПК отдельно проверяется при
> приёмке (вне Docker/браузера не тестировалось).

## 7а. Общий эфир не закончился или нет записи «завершён по времени»

Эфир «до ЧЧ:00» перестаёт действовать **ровно в срок сам по себе**: лента экрана
и панель читают его через `broadcast_rules.effective_on`, не дожидаясь фоновой
задачи. Поэтому экран не залипает на эфире, даже если Celery лежит. От Celery
зависит только порядок в таблице `network_broadcast` и запись в журнале.
1. Эфир нужно прервать раньше срока → «Эфир сети» → «Выключить».
2. Нет записи «Общий эфир завершён по времени» в журнале → проверьте воркер:
   `docker compose logs --tail=50 celery | grep -i broadcast` и
   `docker compose ps celery`; задача `expire_broadcast` запускается раз в минуту.
   Перезапуск: `docker compose restart celery`. Если в первую минуту после
   срока админ успел включить новый эфир или нажать «Выключить», запись «завершён
   по времени» пишет сама панель (API), а не Celery — её отсутствие тогда не
   признак сбоя воркера.
3. Экран всё равно играет эфир после срока → проверьте часы мини-ПК (§9): срок
   передаётся в ленте как `active_until` и сравнивается с часами экрана.

## 7б. Бегущая строка: не бежит, не сошла со срока, страница не открывается

**Разбор «бежит на X из N».** В «Сейчас идут» кнопка «бежит на X из N ▾» раскрывает
экраны, где строка не бежит, с причиной. Что делать:

| Причина | Что значит | Что делать |
|---|---|---|
| не в сети X мин | сигнала от экрана нет дольше 5 минут | §5. Строка придёт с лентой, когда экран выйдет на связь, если срок не вышел |
| старый агент — без подтверждения | агент до 1.4.0: строку показывает по-старому (командой), отчёта не шлёт | обновить агент до 1.4.0 по OTA ([07](../Инструкции/07_ОБНОВЛЕНИЕ_АГЕНТА.md)) |
| остановлен («Стоп») | на экране нажат «Стоп» | кнопка «Показ» — строка вернётся, если срок не вышел |
| экран выключен по расписанию питания | монитор в ночном окне питания | вернётся при включении |
| ждём подтверждения | первые 90 секунд после запуска или правки | подождать |
| не подтвердил — проверьте экран | экран в сети, агент 1.4.0, прошло больше 90 секунд, а он не сообщает, что строка бежит | §7: лог агента, `pgrep -a mpv`; что отдаёт лента: `GET /schedule/minipc/<ID>` (нужен `X-Token` экрана) — в поле `tickers` должна быть строка |

**Строка не ушла с экрана после срока.** Срок снимает сам агент по часам мини-ПК
(связь с сервером не нужна), поэтому первое подозрение — часы: §9. Celery отвечает
только за базу и журнал.

**Нет записи «Бегущая строка снята по сроку» в журнале.** Проверьте воркер:
`docker compose logs --tail=50 celery | grep -i ticker` и `docker compose ps celery`;
задача `expire_tickers` запускается раз в минуту. Перезапуск: `docker compose restart celery`.
Строка при этом перестаёт действовать ровно в срок: панель и лента экрана не показывают
истёкшие строки, не дожидаясь задачи.

**После обновления сервера страница «Бегущая строка» отвечает ошибкой.** Не применена
миграция 034: `bash migrate.sh`. Пока её нет, сигналы экранов, лента, «Стоп» и «Показ»
работают, не работает только сама страница (ошибка в логе API — «бегущая строка не
прочитана…»). Подробности — [08](../Инструкции/08_ОБНОВЛЕНИЕ_СЕРВЕРА.md).

**Строка идёт на всех экранах вместо выбранных или лента не собирается (в логе API —
«бегущая строка не прочитана»), хотя миграция применена.** Вероятная причина:
`migrate.sh` отработал, пока работал **старый** API, и тот создал строки без
`started_at`. Проверка и лечение (повторное применение 034, оно идемпотентно и
трогает только такие строки):
```bash
docker exec ds_postgres psql -U display_user -d display_system -c "SELECT id, message FROM tickers WHERE started_at IS NULL;"
docker exec -i ds_postgres psql -U display_user -d display_system < server/migrations/034_ticker_redesign.sql
docker compose restart api celery
```
Перезапуск api и celery безвреден (на секунды прерывает панель и фоновые задачи) — см.
[08](../Инструкции/08_ОБНОВЛЕНИЕ_СЕРВЕРА.md), «Порядок».

## 8. Проблема после OTA-обновления агентов

**Симптом:** после раската новой версии агенты падают/уходят в офлайн.

1. Масштаб — сколько экранов затронуто (Дашборд).
2. На одном мини-ПК: `journalctl -u ds-agent -n 100` — найти ошибку новой версии.
3. Откат: раскатать предыдущую заведомо рабочую версию через раздел «Обновление
   агентов»; при недоступности — переустановить агент из проверенной папки
   `agent/` (см. [../Инструкции/02_УСТАНОВКА_АГЕНТ.md](../Инструкции/02_УСТАНОВКА_АГЕНТ.md)).
4. Впредь — раскатывать **по группам экранов**, не на всю сеть разом (в плане
   на этап с реальным железом).

## 9. Разъехалось время (расписание играет не вовремя)

1. На сервере: `docker exec ds_ntp chronyc tracking` и `… chronyc sources`.
2. На мини-ПК: `chronyc tracking` — смотрите `System time offset`.
   - Большое смещение: `sudo systemctl restart chrony`, подождите 1–2 минуты.
   - Источники: `chronyc sources` — должен быть виден сервер (`ds_ntp`) и/или
     ВНИИФТРИ/MSK-IX.
3. Помните: учёт показов и расписание — по **московскому времени**; рассинхрон
   искажает и эфир, и отчёты.

## 9а. Команды из панели доходят с задержкой (до 5 секунд)

Признак: «Перезапустить», «Стоп», «Показ», бегущая строка срабатывают не
мгновенно, а через несколько секунд. Значит, WebSocket не поднялся и агент
работает на резервном опросе (polling каждые 5 с).

1. Проверьте, сколько экранов держат WS-соединение:
   `curl -s http://localhost/ws/status` (нужен токен админа) — либо в логе
   агента `/var/log/ds-agent/ds-agent.log` ищите `[WS] Подключён к серверу`.
   Строка `[WS] Handshake не удался` = соединение не устанавливается.
2. Проверьте handshake с сервера:
   ```bash
   curl -s -i -N --max-time 4 -H "Connection: Upgrade" -H "Upgrade: websocket" \
     -H "Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==" -H "Sec-WebSocket-Version: 13" \
     "http://localhost/api/ws/agent/<ID>?token=<ТОКЕН_ЭКРАНА>" | head -3
   ```
   Ожидается `HTTP/1.1 101 Switching Protocols`. Если `404` — nginx и FastAPI
   разошлись в пути (nginx срезает префикс `/api`, роут должен слушать
   `/ws/agent/{id}`); если `502` — не поднят `ds_api`.
3. `docker exec ds_nginx nginx -t` — конфиг должен быть валиден. **Внимание:**
   `nginx.conf` смонтирован как отдельный файл, и правки на хосте контейнер
   не видит до пересоздания: `docker compose up -d --force-recreate nginx`
   (обычный `restart`/`reload` подхватит СТАРУЮ копию).
4. Если панель отдаёт **502 после пересоздания `ds_api`** — проверьте, что в
   `nginx.conf` остались `resolver 127.0.0.11` и `proxy_pass $ds_api`
   (переменная). Именно они заставляют nginx перепроверять адрес апстрима;
   с жёстким `proxy_pass http://api:8000` имя резолвится один раз при старте
   и после смены IP контейнера прокси бьёт в пустоту. Разовое лечение —
   `docker compose restart nginx` (то же делает `selfheal.sh`).
4. Пока WS не поднят, система остаётся работоспособной — команды идут по
   polling, теряется только мгновенность.

## 9б. «Скачать» бэкап или архив диагностики не срабатывает

Бэкап (полный дамп БД) и архив диагностики сервер отдаёт только вошедшему в
панель; бэкап — только администратору и супер-администратору. Кнопка «Скачать»
передаёт вход сама, прямая ссылка `/api/backups/{id}/download` без входа — 401.

- Подсказка «Не удалось скачать: Write access required» — у учётки роль только
  для просмотра (аудитор, модератор). Скачивать бэкап должен администратор.
- Вместо файла открылась вкладка с `{"detail":"Not authenticated"}` — браузер
  держит старую панель (до исправления кнопка была ссылкой). Обновите страницу
  с очисткой кеша: **Ctrl+Shift+R**.
- Вернуло на форму входа — истекла сессия; войдите снова и повторите.
- «Бэкап не найден» / «Файл бэкапа отсутствует на диске» — запись есть, а файла
  в томе `backup_data` нет (удалён руками или ротацией): `docker exec ds_api ls -t /data/backups/`.

## 9в. Миниатюры, просмотр ролика или «Скачать» в медиатеке не работают

Файлы медиатеки сервер отдаёт только вошедшему в панель: миниатюры, кадр
просмотра (`/media/<имя>`) и «Скачать» несут **cookie `ds_media`**, которую
панель берёт при входе (`POST /api/session/media`). Без входа — 401.

- Вместо миниатюр значок ▶, просмотр пишет «Не удалось загрузить файл», в
  консоли браузера (F12) — `401` на `/media/…` или `/thumbnail` → браузер держит
  старую панель (до исправления она cookie не брала): **Ctrl+Shift+R**. Не помогло
  — выйдите и войдите снова. Браузер с запретом cookie файлы показывать не будет.
- `403` — учётка с ролью «рекламодатель» или заблокирована: медиатека ей не положена.
- Проверка с сервера: без входа должно быть 401, по входу — 200 (пароль вводится
  скрыто и в командную строку не попадает).
  ```bash
  curl -s -o /dev/null -w '%{http_code}\n' http://10.0.119.100/media/<файл>                    # 401
  read -rsp "Пароль admin: " P; echo
  T=$(printf %s "$P" | curl -s -X POST http://10.0.119.100/token -d username=admin --data-urlencode password@- \
      | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])"); unset P
  curl -I -H "Authorization: Bearer $T" http://10.0.119.100/media/<файл>                       # 200
  ```
- Без входа `/media/<файл>` отдаёт **200** (а `/api/files/download/<id>` — 401) —
  nginx работает со старой копией `nginx.conf`. Её подхватывает только пересоздание
  (§9а): `docker compose up -d --force-recreate nginx`.
- По входу тоже 401 — `docker compose logs --tail=50 nginx api`: nginx должен
  ходить в `api` за проверкой (`/files/auth`), `docker exec ds_nginx nginx -t`.

## 9г. «Копия на флешку»: не собирается, не скачивается, не отмечается

Функция только для супер-администратора (Настройки → «Копия на флешку»).
Как это устроено: `POST /offsite/copy` собирает копию (минуты) во временной папке
`/tmp/ds_offsite` **внутри контейнера `ds_api`** и выдаёт одноразовую ссылку на 2
минуты (токен лежит в Redis); браузер качает файл; сервер отмечает «скачано» **только
когда файл отдан целиком**. Копии на сервере не хранятся. Что берётся для сборки:
папка проекта, смонтированная в `api` только на чтение (`./:/srv/project:ro`, оттуда
же настоящий `.env`), свежий `pg_dump`, тома документов и OTA.

- **«Сервер не обновлён для копии на флешку: запустите install_server.sh»** (503;
  в панели кнопка «Скачать копию» неактивна) — `api` работает без монтирования
  проекта: код обновили, а контейнер не пересоздали. Лечение — на сервере
  `bash install_server.sh` (его `docker compose up -d` пересоздаёт `api`). Проверка:
  ```bash
  docker exec ds_api ls -a /srv/project | grep -E '^(\.env|docker-compose\.yml)$'   # оба файла на месте
  ```
  Если менялся `nginx.conf`, пересоздайте и nginx: `docker compose up -d --force-recreate nginx`
  (§9а); со старым конфигом (без `location /api/offsite/`) большая копия уходит в
  504 по таймауту 300 с, а «скачано» отмечается раньше, чем файл дошёл до браузера.
- **«Копия уже собирается — подождите и повторите»** (409). Сборка идёт одна за раз;
  на большой базе она занимает минуты, а очень большая может занять и больше
  15 минут, поэтому само по себе «долго» ещё не значит «зависла». Сначала убедитесь,
  что сборка действительно стоит:
  ```bash
  docker top ds_api | grep pg_dump                      # пусто: дамп уже не идёт
  docker compose logs --tail=50 api                     # свежих строк нет, сборка не двигается
  docker exec ds_api ls -la /tmp/ds_offsite             # папка сборки не меняется
  ```
  Если `pg_dump` ещё работает (идёт дамп или шифрование), подождите. Если процесса нет,
  а сообщение держится и новых строк в логе нет, сборка зависла, а замок живёт в
  памяти процесса `api`:
  ```bash
  docker compose logs --tail=100 api | grep "Копия на флешку"
  docker restart ds_api        # снимает замок и стирает остатки сборок в /tmp/ds_offsite
  ```
  Убедитесь, что в этот момент никто не качает файл: перезапуск оборвёт скачивание.
  Затем повторите «Скачать копию».
- **«Хранилище одноразовых ссылок (Redis) недоступно — повторите позже»** (503) —
  лежит Redis: лечение в §4. После подъёма просто повторите скачивание.
- **«Ссылка недействительна или устарела — запросите скачивание заново»** (404) —
  ссылка одноразовая и живёт 2 минуты: её уже открывали (повтор, перезагрузка) или
  браузер долго не начинал скачивание. Нажмите «Скачать» заново.
- **«Файлы роликов не найдены на диске — архив не собран»** (409) — в базе ролики
  есть, а файлов на диске нет. Проверьте том: `docker exec ds_api ls /data/media | head`.
  Если том пуст или потерян — это отдельная авария, [RESTORE_GUIDE](../RESTORE_GUIDE.md).
  Если файлов нет только у части роликов, архив собирается, а панель пишет «В архиве
  не хватает файлов на сервере: N» (такие строки в `MANIFEST_media.txt` помечены
  «нет файла»).
- **В Настройках серая строка «Не удалось загрузить состояние копии»**, напоминания
  на Дашборде нет — панель не получила `GET /offsite/status`. Либо `api` старый (нет
  роутера `offsite`), либо не применена миграция 035 (таблица `offsite_copy_state`):
  `bash migrate.sh`, затем `bash install_server.sh`; проверка — `docker compose logs
  --tail=50 api`.
- **Забыт пароль на копию.** Из панели его не сменить, сброс — только на сервере:
  ```bash
  docker compose exec -T api python /app/reset_offsite_password.py
  ```
  В журнале появится «Пароль на копию сброшен на сервере»; новый пароль задаётся в
  панели. **Старые копии новый пароль не откроет.**
- **В блоке «Пароль на копию» написано «нужно задать заново»** — сменился
  `SECRET_KEY` (им зашифрован сохранённый пароль; например, пересоздали `.env`).
  Сохранённый пароль уже не прочитать: задайте новый (текущий не спрашивается).
- **Файл скачан целиком, а напоминание не стало зелёным.** Панель после начала
  скачивания опрашивает сервер каждые 15 с, но не дольше часа, и перезагрузка
  страницы этот опрос сбрасывает: обновите страницу (F5). Если отметки нет и после
  этого — смотрите журнал («Копия на флешку скачана») и лог:
  ```bash
  docker compose logs --tail=100 api | grep "не удалось отметить скачивание"
  ```
  Такая строка значит, что база была недоступна в момент отметки: файл целый, но
  сервер его не записал, напоминание честно остаётся жёлтым. Починьте базу (§2) и
  скачайте копию ещё раз. Если скачивание оборвали на середине, отметки нет, и это
  правильно.
- **Копии копятся на диске сервера?** Не должны: после скачивания папка стирается,
  неоткрытая — через ~15 минут, при старте `api` — всё. Проверка: `docker exec ds_api ls -la
  /tmp/ds_offsite` — пусто или одна свежая папка. Там расшифрованный архив с `.env`,
  поэтому лишнее стирайте сразу: `docker restart ds_api`.
- **На флешке копия не открывается** (это уже на новой машине, по `ВОССТАНОВЛЕНИЕ.txt`):
  «ФАЙЛ ПОВРЕЖДЁН» — скопируйте файл с флешки ещё раз, не помогло — берите копию
  за предыдущий день; «bad decrypt» — неверный пароль на копию (копия открывается
  тем паролем, который действовал в день её создания; проверьте раскладку и
  Caps Lock). Общая процедура — [RESTORE_GUIDE, Сценарий 0](../RESTORE_GUIDE.md).
- Если заливка дампа из **ночного бэкапа** (не из копии на флешку) печатает
  `ERROR: unrecognized configuration parameter "transaction_timeout"` — это
  безвредная строка, объяснение в RESTORE_GUIDE (примечание к Сценарию 1).

## Эскалация / что сохранить для разбора
- **Собрать всю диагностику одной командой** (секреты/токены замаскированы):
  `bash collect_diag.sh` (на сервере) или `bash agent/collect_diag_agent.sh` (на мини-ПК).
- Логи упавшего сервиса: `docker compose logs --tail=500 <сервис> > /tmp/<сервис>.log`.
- Логи агента: `/var/log/ds-agent/ds-agent.log` и `journalctl -u ds-agent`.
- Момент и симптом (что перестало работать, после чего).
- Не удаляйте тома (`postgres_data`, `media_data`, `minio_data`, `backup_data`) —
  в них данные и бэкапы для восстановления.
