# Комплект для установки и восстановление одной командой — описание

Дата: 2026-11-09. Продолжение «Копии на флешку» (`docs/superpowers/specs/2026-11-03-offsite-copy-design.md`,
§11 «Комплект для установки без интернета»; влито в main = d89ddbc).
Макеты: `docs/superpowers/specs/2026-11-09-offline-kit-restore-mockups.html` — одобрены пользователем 09.11:
1 — Настройки, 2 — дашборд, 3 — терминал на чистой машине, 4 — терминал поверх старой установки.

## 1. Зачем

Пользователь хочет, чтобы при **любой поломке** работу системы можно было восстановить **быстро и без
проблем**, и под «без проблем» понимает в том числе **меньше ручной работы: одна команда** (его слова).

Сейчас по копии на флешке система поднимается по `ВОССТАНОВЛЕНИЕ.txt` в семь ручных шагов. Шаг 3 —
`install_server.sh`, который **собирает** образы из интернета (`docker compose up -d --build`): базовые образы
с Docker Hub, пакеты Debian, библиотеки Python. Машина взамен будет с Astra **и с интернетом** (ответ
пользователя), так что комплект нужен не из-за отсутствия сети, а потому что сборка в день аварии может не пройти
или пройти иначе: Docker Hub из России бывает недоступен, плавающие теги (`python:3.11-slim`, `nginx:alpine`,
`postgres:15-alpine`) и пакеты уходят вперёд — сервер соберётся не таким, каким работал (пример уже был:
`pg_dump` 17 в образе против базы 15). Пользователь подтвердил это понимание.

## 2. Цели, не цели, анти-цели

**Цели**
- После каждой успешной выкатки сервер сам сохраняет **комплект для установки**: ровно те образы, на которых он
  работает, плюс модуль `docker compose`. Хранится только последний.
- Суперадмин скачивает комплект из панели (блок «Копия на флешку») — **раз на версию**; панель напоминает,
  если после выкатки новый комплект ещё не скачан.
- **Восстановление одной командой**: человек вставляет флешку, вводит одну строку, и скрипт сам ставит Docker
  (если его нет), программу (из комплекта — без сборки и без интернета; без подходящего комплекта — сборкой
  через интернет, как сейчас), возвращает базу, документы, файлы OTA и ролики, сверяет контрольные числа
  и пишет итог.
- Восстановление работает **и на чистой машине, и поверх старой установки** на той же машине. Порядок пользователя:
  «сначала пробуем восстановить; если не сработало — переустанавливаем» (Astra), и запускаем ту же команду.
- Поверх старой установки — **с возможностью вернуться**: прежнее состояние сохраняется, вернуть его можно одной
  командой.
- Учения на стенде: «чистая машина» без выхода в интернет поднимается по флешке; восстановление поверх старой
  установки и возврат «как было» проходят.

**Не цели**
- Пакеты самого Docker на флешке (полностью без интернета и без репозитория Astra). Docker ставится из
  репозитория Astra (решение пользователя, §4.6).
- Похудение образа `api` (в нём остаются `gcc`/`python3-dev`), закрепление базовых образов по digest, версия
  `pg_dump` в ночных дампах, рост зеркала MinIO — отдельные задачи.
- Откат неудачной выкатки «назад на прошлую версию» как отдельная функция. Он получается сам: выбрать на флешке
  более старую копию, скрипт возьмёт подходящий к ней комплект (§5.5), если он сохранён на флешке.
- Кнопка обновления сервера в панели (решено раньше: сервер обновляют с хоста `install_server.sh`).

**Анти-цели** (провал, даже если «работает»)
- Восстановление «прошло», а система не та: база не совпала с описью, ролики не все, сервер собран не из
  комплекта, хотя комплект подходил, — и скрипт об этом молчит.
- Скрипт поверх старой установки что-то изменил до ввода «ДА», или после «ДА» вернуться к прежнему состоянию нельзя.
- Комплект попал в ежедневную копию (она раздуется на сотни мегабайт) или комплекты копятся на диске сервера.
- Панель показывает «комплект скачан», а файл до браузера не дошёл.
- Пароль на копию или пароли из `.env` видны в выводе, в логе, в списке процессов (`ps`) или остались на диске
  после успешного восстановления вне папки программы.
- Человеку приходится что-то набирать сверх одной строки и трёх ответов (какая копия, пароль sudo, пароль
  на копию; поверх старой установки — ещё «ДА»).

## 3. Что есть сейчас

- `install_server.sh`: preflight (Docker, Compose v2, место, часы) → `.env` (существующий не трогает) →
  `docker compose up -d --build` → `migrate.sh` → при первой установке пароль admin → самопроверка 7 контейнеров,
  БД, панели → итог PASS/FAIL. Выкатки сервера идут через него (док 08).
- `docker-compose.yml`: `api` и `celery` — `build: ./server` без `image:`; `ntp` — `build: ./ntp`. Имена собранных
  образов зависят от **имени проекта Compose** (по умолчанию — имя папки): `video_minipc_v162_modular-api`,
  `dsdev-api`… От имени проекта зависят и **имена томов** с данными. Остальные: `postgres:15-alpine`,
  `redis:7-alpine`, `minio/minio:RELEASE.2022-10-24T18-35-07Z`, `nginx:alpine`.
- В `api`/`celery` код приходит с хоста (`./server:/app`), из образа используются только окружение: Python и
  библиотеки (`server/requirements.txt`), ffmpeg, клиент PostgreSQL. `ntp` копирует `ntp/chrony.conf` в образ.
  `.dockerignore` нет.
- Замер на стенде (Mac, arm64): все образы стека, `docker save | gzip -1` — **≈ 760 МБ**, ≈ 10 с. Образы с Mac на
  сервер не годятся (другой процессор), поэтому комплект делает сам сервер.
- «Копия на флешку» (`server/offsite_store.py`, `offsite_rules.py`, `routers/offsite.py`,
  `static/js/views/offsite.js`, миграция 035): ежедневная копия `ds_copy_ГГГГ-ММ-ДД_ЧЧММ.tar` (внешний tar:
  `ВОССТАНОВЛЕНИЕ.txt` + `copy.tar.gz.enc` + `.sha256`; внутри — `program/` с `.env`, `db/backup_*.sql.gz`,
  `documents/`, `media_documents/`, `agent_updates/`, `MANIFEST.txt` с контрольными числами), архивы роликов
  `ds_media_new_*/ds_media_all_*.tar` (`media/<файл>` + `media/MANIFEST_media.txt`). Скачивание — по одноразовой
  ссылке (тикет в Redis, 2 мин); «скачано» отмечается только после последнего байта. Состояние —
  `offsite_copy_state` (id = 1). Только суперадмин. Корень проекта виден `api` только на чтение
  (`./:/srv/project:ro`); `is_program_excluded` решает, что из него идёт в копию.
- Шифрование копии — формат `openssl enc` (`OPENSSL_DECRYPT_CMD`), проверено на OpenSSL 1.1.1n (как в Astra 1.7).
- Учения «Копии на флешку» (07.11) прошли по `ВОССТАНОВЛЕНИЕ.txt` дословно, но на машине с интернетом и с
  установленным Docker.
- Как Docker поставлен на боевом сервере 10.0.119.100 — **неизвестно** (пользователь не помнит, доступа нет).
  Что известно: в репозитории Astra 1.7 есть `docker.io` (Engine 20.10); модуля `docker compose` v2 там,
  насколько известно, нет — только старый `docker-compose` v1.

## 4. Решения пользователя

1. Машина взамен — с Astra и с интернетом. Комплект — от сборки из интернета, не от отсутствия сети (§1).
2. Образы сохраняет сервер после каждой успешной выкатки; отдельный файл в блоке «Копия на флешку»; скачивать
   раз на версию; напоминание, если новый не скачан. В ежедневную копию не класть.
3. Восстановление — **одной командой**: программа, база, файлы, ролики (а не семь ручных шагов).
4. Нужен и случай «поверх старой установки на той же машине»: сначала пробуем восстановить, не вышло —
   переустанавливаем Astra и запускаем ту же команду.
5. Поверх старой установки: **предупреждение с вводом «ДА»** и **сохранение прежнего состояния с возможностью
   вернуться** (пользователь отдельно отказался от варианта «без возврата»).
6. Docker Engine скрипт ставит сам из репозитория Astra (`apt install docker.io`); модуль `docker compose` v2 — из
   комплекта (сервер копирует свой). Проверить на настоящей Astra — при первом доступе к серверу (§10).
7. Копия: по умолчанию самая свежая; скрипт показывает список копий на флешке, можно выбрать более старую.
8. Комплект: если их на флешке несколько, скрипт сам выбирает тот, что подходит к программе из выбранной копии.
9. Макеты 1–4 одобрены: строка «Комплект для установки» в трёх состояниях; строка в том же жёлтом баннере
   дашборда; ход восстановления в терминале; предупреждение, «ДА» и команда возврата.
10. ЗПС (замкнутая программная среда Astra) на сервере **не включена**; новая машина — так же.
11. Сломалось после «ДА» (поверх старой установки) — скрипт **останавливается**, честно пишет, на каком шаге, и
    даёт на выбор две команды: «повторить» и «вернуть как было» (`rollback.sh`). Сам ничего не откатывает:
    человек сидит у терминала и решает сам.

## 5. Как устроено

### 5.1 Комплект: что внутри и когда сохраняется

Один файл `ds_kit_ГГГГ-ММ-ДД_ЧЧММ_<версия8>.tar` (несжатый внешний tar, как копия) в папке **`offline_kit/`
в корне проекта** на сервере. Внутри:
- `images.tar.gz` — `docker save` всех образов стека одной командой (общие слои один раз), сжатый;
- `docker-compose` — модуль Compose v2, скопированный с сервера (путь — из `docker info`, поле плагинов
  клиента); если найти не удалось — комплект сохраняется без него и `KIT.txt` об этом говорит;
- `KIT.txt` — опись: когда и на какой машине сохранён, **архитектура** (`uname -m`), **версия** и
  **отпечаток программы** (ниже), список образов (имя:тег → ID), версия Docker сервера, sha256 файлов комплекта.

Рядом с файлом — маленький `offline_kit/KIT.json` (то же, что в `KIT.txt`, для панели: читать tar на каждый
опрос статуса не нужно).

Два разных числа:
- **Отпечаток программы** — отвечает на вопрос «подходит ли комплект к программе». sha256 от входов, из которых
  строятся образы: содержимое `server/Dockerfile`, `server/requirements.txt`, `ntp/Dockerfile`, `ntp/chrony.conf`
  и строки `image:` из `docker-compose.yml` (после нормализации пробелов). Код сервера в отпечаток не входит:
  он приходит с хоста (`./server:/app` у `api` и `celery`).
- **Версия** — отвечает на вопрос «этот ли файл уже скачан». sha256 от набора ID образов в комплекте. Короткая
  форма (8 знаков) — в имени файла и в панели.

Правило отпечатка задаётся **в одном месте** — `kit_fingerprint.sh` в корне проекта (функция, которую
подключают `install_server.sh` и скрипт восстановления); панель считает его на Python по тому же правилу, и
pytest сверяет оба расчёта на одних и тех же файлах.

**Когда сохраняется.** В конце `install_server.sh`, только если самопроверка прошла (`FAIL = 0`), отдельным
шагом «Комплект для установки». Не пересохраняется, если ID образов те же, что в существующем `KIT.json`
(обычная выкатка без смены `Dockerfile`/библиотек — секунды, а не минуты). Новый файл пишется во временный,
проверяется (`gzip -t`, sha256) и только потом заменяет старый; старый удаляется — **на диске всегда не больше
одного комплекта**. Перед сохранением — проверка места (нужно ≈ 2 размера прошлого комплекта, без прошлого —
1,5 ГБ); мало места, ошибка `docker save` или нет `gzip` — **предупреждение** (⚠) с подсказкой, а не провал
установки: сервер уже работает. Флаг `--no-kit` пропускает шаг (для стендов, где он не нужен).

**`offline_kit/`** — в `.gitignore` и в `is_program_excluded` (в копию программы не идёт).

**Образ `api`/`celery` — без кода сервера** (мой выбор, найдено проверкой описания). Сейчас `server/Dockerfile`
кончается `COPY . .`: код попадает в образ, и любая правка кода даёт новый ID образа — новую «версию» комплекта
почти на каждой выкатке, минуты `docker save` и напоминание «скачайте новый» каждый раз. Это ломает «раз на
версию». Поэтому в образ из `./server` идёт только `requirements.txt` (через `server/.dockerignore` или правку
`Dockerfile` — решает строитель). Работе сервера это не мешает: оба сервиса и сейчас берут код с хоста
(`./server:/app`), код из образа перекрыт и не используется. Тогда образы меняются только вместе с отпечатком.

**Секретов в комплекте нет**: `.env` лежит в корне проекта и в образ не попадает, кода в образе нет.

### 5.2 Имена образов не зависят от папки

Чтобы загруженные из комплекта образы подхватились без сборки в любой папке, у собираемых сервисов появляются
постоянные имена (`image:` в `docker-compose.yml`; например `ds-server:latest` для `api` и `celery`,
`ds-ntp:latest`). **Имя проекта Compose не меняется** — от него зависят имена томов с данными, его смена
«потеряла» бы базу и ролики на боевом сервере. Как совместить `build` + одно `image:` у двух сервисов, чтобы
сборка шла один раз и `up --no-build` не тянул ничего из сети, — решает строитель (проверка — учения).
Неудобство для нескольких стендов на одной машине разработчика (одно имя образа на всех) — допустимо; строитель
может развести стенды переменной в имени образа, если это не усложняет боевой путь.

### 5.3 Панель (макеты 1 и 2)

**Настройки → «Копия на флешку»**, третья строка «Комплект для установки» (только суперадмин, как весь блок):
- **А** — комплект на сервере есть, эту версию ещё не скачивали: кнопка «⤓ Скачать комплект · N МБ», версия
  (дата сохранения и 8 знаков), «Последнее скачивание: … — прошлая версия, скачайте новую» (жёлтым), подсказка
  не удалять с флешки старые комплекты, пока там лежат старые копии.
- **Б** — эта версия уже скачана: «⤓ Скачать ещё раз», «— эта версия ✓».
- **В** — комплекта на сервере нет (выкатки с этой функцией не было, сохранение не удалось): кнопка неактивна,
  «Комплект ещё не сохранён. Он появится после следующей выкатки (bash install_server.sh). Без него
  восстановление тоже пройдёт, но соберёт программу из интернета».
- Дополнительно (мой выбор): если отпечаток комплекта **не совпадает** с программой, которая сейчас лежит в
  проекте (кто-то поменял `Dockerfile`/библиотеки без `install_server.sh`), строка показывает предупреждение
  «Комплект не подходит к нынешней программе — запустите bash install_server.sh», скачать всё равно можно.
- Пароль входа заново **не** спрашивается: в комплекте нет ни паролей, ни данных (как у роликов).

**Дашборд**: баннер «Копия на флешку» жёлтый, пока не скачано хоть что-то из трёх — сегодняшняя копия, новые
ролики, **комплект текущей версии**. Строка «После выкатки ДД.ММ обновился комплект для установки — скачайте его
(N МБ)»; если копия и ролики скачаны, а комплект нет — заголовок «Скачайте новый комплект для установки» и
главная кнопка «⤓ Скачать комплект». Состояние **В** баннер жёлтым **не** делает (мой выбор: в панели с этим
ничего не сделать, сообщение есть в Настройках).

**Сервер**:
- `GET /offsite/status` получает раздел `kit`: есть ли комплект, файл, размер, версия, дата сохранения,
  архитектура, совпадает ли отпечаток с программой, кто/когда/какую версию скачал последней, скачана ли текущая.
  Правило напоминания (`reminder_state`) учитывает комплект: `warn`, если комплект есть, подходит к программе
  и его версия ≠ последней скачанной.
- `POST /offsite/kit` (суперадмин) → одноразовая ссылка, как у копии; `GET /offsite/download` с видом `kit`
  отдаёт файл из `/srv/project/offline_kit/` потоком; «скачано» и запись в журнал операций («Скачан комплект
  для установки: версия …, N МБ») — **только после последнего байта**. Нет комплекта — 409 с понятным текстом.
- Миграция `036_offsite_kit.sql`: в `offsite_copy_state` — кто, когда, какой файл, какую версию и сколько байт
  комплекта скачали. Строку initdb — в `docker-compose.yml` (правило проекта).
- Через nginx комплект идёт той же локацией `/api/offsite/` (таймауты и отключённая буферизация там уже есть).

### 5.4 `install_server.sh` с комплектом

Новый режим `bash install_server.sh --kit ПУТЬ/ds_kit_….tar` (им пользуется скрипт восстановления; годится и для
первой установки новой площадки без сборки):
1. Проверяет комплект: целостность (sha256 из `KIT.txt`), архитектуру (≠ `uname -m` → ОСТАНОВ с понятной
   причиной), отпечаток против программы в этой папке (не совпал → ОСТАНОВ «комплект от другой версии программы»).
2. Ставит модуль `docker compose` из комплекта, если `docker compose version` не отвечает (в системный каталог
   плагинов Docker).
3. `docker load`, затем запуск **без сборки и без скачивания** (`--no-build`, без pull), далее как обычно:
   миграции, самопроверка.
4. После успешной установки кладёт этот же комплект в `offline_kit/` (копией, не пересохранением), чтобы панель
   нового сервера сразу его показывала.

Без `--kit` — как сейчас (сборка через интернет) плюс сохранение комплекта (§5.1). Время по часам хоста
(preflight) без сети проверяется грубо, как и сейчас, — это не блокер.

### 5.5 Восстановление одной командой (макет 3)

Скрипт `restore.sh` лежит **открыто во внешнем tar ежедневной копии** рядом с `ВОССТАНОВЛЕНИЕ.txt` (в репозитории —
файл в корне проекта; `build_copy` кладёт его во внешний tar). Человек открывает терминал в папке флешки и
вводит одну строку (её печатают панель — с именем последней скачанной копии — и `ВОССТАНОВЛЕНИЕ.txt`):

    tar -xf ds_copy_2026-11-08_0915.tar restore.sh && bash restore.sh

Строка должна работать на флешке exFAT/NTFS и с `noexec` (запуск через `bash`, не `./`). Папка флешки = папка,
где лежит скрипт; рабочая папка — на диске машины (`~/ds_restore`), не на флешке.

Ход (вопросы — только выделенные):
1. **Какую копию восстановить?** — список `ds_copy_*.tar` на флешке (по дате из имени), Enter — самая свежая.
2. **Проверка машины**: ОС (Astra/Debian, `/etc/astra_version` если есть), место (оценка по размерам файлов на
   флешке, с запасом), Docker:
   - нет Docker → `sudo apt-get install -y docker.io` (из настроенных репозиториев Astra), включить и запустить
     службу. **Пароль sudo** спрашивается один раз. apt не смог → ОСТАНОВ с подсказкой (интернет / репозиторий
     Astra / команды для ручной установки);
   - пользователь не в группе `docker` → скрипт работает с Docker через `sudo` и добавляет пользователя в группу
     на будущее (с сообщением), без выхода из системы;
   - нет `docker compose` v2 → ставится из выбранного комплекта; комплекта нет → ОСТАНОВ с подсказкой.
   - Адрес машины сверяется с адресом старого сервера из `MANIFEST.txt`: не совпал → предупреждение, что экраны
     ищут сервер по старому адресу, и вопрос «продолжить? (да/нет)».
3. **Пароль на копию** — читается скриптом без эха и передаётся `openssl` не через аргументы командной строки.
   Проверка sha256, расшифровка, распаковка в `~/ds_restore`. Неверный пароль → повторить ввод (до 3 раз).
4. **Есть ли старая установка** (§5.6). Есть → предупреждение, «ДА», сохранение прежнего состояния.
5. **Программа**: из копии — в постоянную папку (`~/digital-signage` на чистой машине; на старой установке — в ту же
   папку, где она стояла, чтобы имя проекта и тома остались прежними). Комплект: среди `ds_kit_*.tar` на флешке
   выбирается тот, чей отпечаток совпал с программой из копии и чья архитектура совпала с машиной (из нескольких
   таких — тот, чья версия записана в `MANIFEST.txt` копии: сервер пишет туда версию своего комплекта на момент
   копии; нет такого — самый свежий из подходящих); нашёлся →
   `install_server.sh --kit`; не нашёлся → обычный `install_server.sh` (сборка через интернет) с прямой строкой
   «подходящего комплекта нет — собираю из интернета». Копии, снятые до этой работы, всегда идут сборкой.
6. **Данные**: база (тот же блок, что шаг 4 инструкции: стоп api/celery, пересоздать базу, залить дамп с
   `ON_ERROR_STOP`, `migrate.sh`, старт), документы рекламодателей, «Документы» медиатеки, файлы OTA, ролики из
   **всех** `ds_media_*.tar` на флешке (в одну папку, без `MANIFEST_media.txt`).
7. **Сверка**: контрольные числа базы против `MANIFEST.txt` — должны совпасть точно (их снимали сразу после дампа);
   7 контейнеров запущены; `/health`; панель отвечает через nginx. Число роликов на диске против описей архивов.
8. **Уборка**: `~/ds_restore` удаляется (в нём `.env` и расшифрованное); в папке программы `.env` остаётся — он
   нужен серверу.
9. **Итог**: «✅ ВСЁ ВОССТАНОВЛЕНО (N мин)», адрес панели, «вход прежним логином и паролем», экраны выйдут на связь
   сами; поверх старой установки — ещё команда возврата. Не вышло — «✗ …» с тем, на каком шаге, что делать, и
   где лог. Поверх старой установки после «ДА» (решение пользователя §4.11) — останов на этом шаге и две
   готовые команды на выбор: повторить восстановление и `rollback.sh`; автоматического отката нет. Несовпадение
   контрольных чисел — такой же останов (✗), не «успех с оговоркой».

Весь вывод дублируется в лог (как у `install_server.sh`), **без паролей**. Повторный запуск после обрыва начинает
с начала и ничего не портит: рабочая папка пересоздаётся, база пересоздаётся блоком, ролики докладываются.
Свою же недоделанную установку (на чистой машине) скрипт узнаёт по метке и **не** считает «старой установкой»:
лишнего «ДА» и лишнего сохранения состояния нет.

### 5.6 Поверх старой установки и возврат (макет 4)

- **Обнаружение**: есть контейнеры стека (`ds_api` и др., запущены или нет) — папка установки берётся из меток
  Compose контейнера; либо существует целевая папка программы. Ни одного изменения до «ДА».
- **Предупреждение**: какая установка найдена (папка, запущена ли), от какой даты копия, что пропадёт (всё, что
  появилось после даты копии: ролики в медиатеке, правки расписания и показов, журнал показов, пользователи),
  куда будет сохранено прежнее состояние, сколько нужно места и сколько свободно. Места мало → ОСТАНОВ до «ДА».
  Продолжение — только после ввода «ДА» (регистр не важен).
- **Сохранение прежнего состояния** в `~/ds_before_restore_ГГГГ-ММ-ДД_ЧЧММ/`:
  - **база** — так, чтобы вернуть можно было **даже если она не запускается** (предпочтительно — файлы тома
    PostgreSQL при остановленной базе, через временный контейнер из того же образа postgres; строитель может
    выбрать иначе при том же свойстве);
  - **папка программы** — переносится целиком (с её `.env`);
  - **образы** прежней установки — получают отдельную метку, чтобы загрузка комплекта их не затёрла;
  - **`rollback.sh`** — возврат одной командой.
  Ролики, документы и файлы OTA восстановление **только добавляет** и ничего не удаляет, поэтому их сохранять не
  нужно: после возврата лишние файлы не мешают. Тома MinIO и Redis не трогаются.
- `selfheal.sh` по cron (`/etc/cron.d/ds-selfheal`, если его ставили) не должен поднимать стек посреди
  сохранения и восстановления: скрипт ставит замок, который `selfheal.sh` уважает (cron не трогаем).
- Прежние папки `ds_before_restore_*` **никогда** не перезаписываются и не удаляются скриптом (второй запуск
  создаёт новую и напоминает о существующих). Удалять их — решение человека; итог об этом говорит.
- **`rollback.sh`**: спрашивает «ДА»; останавливает стек; откладывает текущую папку программы (не удаляет);
  возвращает сохранённую папку и метки образов; возвращает базу; запускает; самопроверка; итог «ВЕРНУЛ КАК БЫЛО».

### 5.7 Docker на Astra

Скрипт ставит `docker.io` из репозитория Astra (§5.5, п. 2), модуль Compose — из комплекта. ЗПС на сервере не
включена (§4.10); скрипт всё же проверяет её состояние, если на машине есть средства Astra для этого, и при
включённой ЗПС останавливается до любых изменений с объяснением (модуль Compose из комплекта не подписан).
Отсюда два риска,
которые на стенде не проверить (§10): совместим ли модуль Compose с сервера с Engine из репозитория Astra (20.10),
и загружает ли этот Engine образы, сохранённые Docker сервера. Если на учениях или на Astra выяснится, что
связка не работает, запасной путь в подсказке ОСТАНОВА — поставить Docker с сайта Docker по инструкции; в
описи комплекта есть версия Docker сервера, чтобы поставить такую же.

## 7. Безопасность — сводка

- Комплект без секретов; скачивает только суперадмин, по одноразовой ссылке; журнал операций.
- Пароль на копию: ввод без эха, в `openssl` не через аргументы (не виден в `ps`), не пишется в лог.
- `~/ds_restore` удаляется после успеха; при ошибке итог прямо говорит, что там лежат пароли и как удалить.
- `ds_before_restore_*` содержит `.env` и базу прежней установки — права только владельцу (700), итог говорит об
  этом.
- Скрипт с `sudo` делает только перечисленное (apt, служба Docker, группа `docker`, каталог плагинов, команды
  Docker); ничего не скачивает мимо apt и Docker.

- **pytest**: отпечаток Python = отпечаток `kit_fingerprint.sh` на одних файлах (и меняется от каждого входа, не
  меняется от кода сервера); статус `kit` во всех состояниях А/Б/В и при несовпавшем отпечатке; напоминание с
  комплектом; `POST /offsite/kit` — 403 для не-суперадмина, 409 без комплекта; ссылка одноразовая; «скачано» и

  `restore.sh` есть во внешнем tar копии; миграция 036 и её строка в compose; `bash -n` для `restore.sh`,
  `install_server.sh`, `kit_fingerprint.sh`.
- **smoke** (под существующим флагом «Копии на флешку»): если комплект на стенде есть — скачать по ссылке,
  проверить tar, `KIT.txt`, sha256 и отметку «скачано».
- **E2E**: строка комплекта (А/Б/В — сколько состояний достижимо на стенде), строка в баннере дашборда.
- **Учения на стенде** (главная проверка; Docker-команды требуют выхода из песочницы — с согласия пользователя):
  1. `install_server.sh` на стенде сохраняет комплект (настоящий `docker save`); повторный запуск без изменений
     образов — не пересохраняет.
  2. Скачать копию, ролики и комплект через панель/API в папку-«флешку».
  3. **«Чистая машина без интернета»**: контейнер Debian 11 (Docker Engine 20.10 из `docker.io`, как в Astra 1.7)
     в привилегированном режиме, в docker-сети **без выхода наружу**, с подключённой «флешкой». Одна строка из
     инструкции → «ВСЁ ВОССТАНОВЛЕНО»; числа = опись; md5 роликов, документов и файлов OTA совпали; вход прежним
     паролем admin; 7 контейнеров; доказательство, что ничего не скачивалось (сеть закрыта, `docker pull` падает).
  4. **Поверх старой установки** в той же «машине»: добавить ролик и пользователя → восстановить более старую копию
     с «ДА» → их нет; `rollback.sh` → они вернулись, система работает. Повторный запуск после обрыва посередине —
     проходит.
  5. **Без комплекта**: без интернета — понятный ОСТАНОВ; с интернетом — сборка и восстановление проходят.
  6. **Установка Docker скриптом**: тот же Debian 11 без Docker, с доступом к репозиторию — скрипт ставит
     `docker.io` и модуль Compose из комплекта. (Как запускать службу без systemd в контейнере — решает строитель.)
  7. Несовпадение архитектуры и отпечатка — понятный отказ `--kit` и переход на сборку.
  Учения — на образах arm64 (Mac); на сервере x86_64 комплект делает сам сервер. «Сервер» учений, который
  сохраняет комплект, — тоже Linux-контейнер с Docker внутри, а не сам Mac: на Mac модуль Compose — программа для
  macOS, а `uname -m` пишет `arm64`, а не `aarch64`, как Linux.

## 12. Решения, принятые мной (проверьте при чтении), и что оставлено строителю

**Мои решения**
1. Скрипты называются латиницей — `restore.sh` и `rollback.sh` (в макетах — `ВОССТАНОВИТЬ.sh`/`ВЕРНУТЬ.sh`):
   строку команды часто набирают руками, а кириллица требует переключения раскладки (та же причина, по которой
   пароль на копию — только латиница).
2. Два числа — «отпечаток» (подходит ли к программе) и «версия» (скачана ли); комплект не пересохраняется, если
   образы не изменились.
3. Комплект хранится в `offline_kit/` в корне проекта; без пароля входа при скачивании; не делает баннер жёлтым,
   пока его на сервере нет; предупреждение, если комплект не подходит к нынешней программе.
4. Сбой сохранения комплекта — предупреждение, а не провал установки.
5. Поверх старой установки программа ставится в ту же папку (имя проекта и тома прежние); прежнее состояние —
   база (переживает «база не запускается»), папка программы, метки образов; ролики не сохраняются (восстановление
   их только добавляет). Папки `ds_before_restore_*` скрипт не удаляет.
6. Пользователь не в группе `docker` — скрипт работает через `sudo` и добавляет его в группу на будущее.
7. Контрольные числа должны совпасть точно; неверный пароль на копию — до 3 попыток.
8. «Чистая машина» на учениях — Debian 11 с `docker.io` 20.10 (ближе всего к Astra 1.7), сеть закрыта.
9. Образ `api`/`celery` — без кода сервера (только окружение), иначе комплект менялся бы на каждой выкатке.
10. Копия записывает в `MANIFEST.txt` версию комплекта сервера; восстановление предпочитает именно его.

**Оставлено строителю**: как совместить `build` + `image:` у `api`/`celery`; как убрать код из образа
(`.dockerignore` или `Dockerfile`); формат и место `rollback.sh`; способ сохранить базу при том же свойстве;
оценка нужного места; разметка строк в панели в пределах макетов; как поднять `dockerd` в контейнере учений.
