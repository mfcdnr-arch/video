# Установка агента с сервера и единый образ мини-ПК — черновик описания

Дата: 2026-11-07. **Статус: черновик обсуждения, не согласован, ничего не реализовано.**
Обсуждение продолжается: открытые вопросы — в §6. После ответов будет полное описание, его прочитает
рецензент, затем план реализации.

Пометки в тексте: **(решение пользователя)** — сказано пользователем; **(предложение)** — мой вариант,
пользователь его ещё не принял; **(догадка)** — не проверено.

## 1. Зачем

Сейчас агент ставится на каждый мини-ПК вручную. Сотрудник переносит папку проекта на ПК, запускает
`install.sh` с токеном из панели, а потом отдельно включает автологин и режим питания в графических
утилитах Astra. Это долго, токен переносится руками, а ПК получаются настроены по-разному.

Хотим **(решение пользователя)**: один образ на все ПК. Сотрудник ставит систему, подключает ПК к сети и
экрану, а агента ставит администратор из панели. После этого всё работает как на пилоте: автологин,
полноэкранный показ, точное время, команды из панели, OTA.

## 2. Цели, не цели, анти-цели

**Цели**
- Один установочный носитель на все ПК; после установки ПК настроены одинаково.
- Агент ставится по команде администратора из панели, без копирования папки и токена руками
  **(решение пользователя)**.
- Работают оба способа адресации: статический IP — основной, DHCP — тоже **(решение пользователя)**.
- Сотрудник на площадке прямо на мониторе видит, дошёл ли ПК до сервера **(предложение)**.

**Не цели** **(предложение)**
- Установка ОС по сети (PXE): сотрудник и так ставит систему на месте.
- Переделка агента сверх того, что нужно для установки.

**Анти-цели** **(предложение)**
- После перезагрузки ПК — чёрный экран или экран входа (автологин не сработал).
- На сервере лежит ключ или пароль, открывающий все ПК сети.
- Пароли или токены открытым текстом на флешке или в git.

## 3. Что есть сейчас и что сломано

### 3.1 Как ставится агент сейчас

1. Панель: «Экраны» → «Добавить экран» → «Создать и получить токен». Панель один раз показывает ID,
   токен и готовую команду установки.
2. На мини-ПК вручную переносят папку проекта (нужны `install.sh` и `agent/`). Скрипта сборки пакета
   агента в репозитории нет, сервер установщик не раздаёт.
3. `sudo bash install.sh http://10.0.119.100 ТОКЕН ID toor`.
4. Вручную: автологин в `fly-admin-dm`, питание «Никогда», перезагрузка и проверка.

`install.sh` делает 10 шагов: проверки → apt (`python3`, `pip`, `venv`, `mpv`, `chrony`, `curl`) →
каталоги → venv с `requests` из PyPI → проверка `/health` сервера → `/etc/ds-agent/config.ini` и
`screen_id` → sudoers NOPASSWD на `reboot` и `systemctl restart ds-agent` → chrony (ВНИИФТРИ, MSK-IX,
сервер) → автологин только для LightDM и `~/.config/kscreenlockerrc` → служба `ds-agent` от `toor`,
самопроверка, лог `/var/log/ds-agent-install.log`.

Дальше OTA заменяет только файлы из `ALLOWED_AGENT_FILES` (`server/routers/agent_ota.py`) в
`/opt/ds-agent`. Службу, конфиг, sudoers и сам `ds_ota_updater.py` OTA не обновляет.

### 3.2 Найденные проблемы (решение пользователя: исправить позже)

1. **Служба, вероятно, запрещает sudo.** В `agent/ds-agent.service` стоит `NoNewPrivileges=true`, а при
   нём `sudo` не может повысить права. По коду:
   - «Перезагрузка» (`agent/ds_sync.py`, `sudo reboot`) не перезагрузит ПК, хотя команда уже
     подтверждена серверу;
   - OTA (`agent/ds_ota_updater.py`) заменит файлы, но рестарт не пройдёт, а код возврата не
     проверяется — старый код работает до следующего перезапуска;
   - «Перезапустить» срабатывает через запасной путь `os.execv`.

   Коммит `b93f1f3` объяснял похожий симптом OTA путём в sudoers; возможно, настоящая причина здесь.
   На железе не проверено. Проверка на пилоте: нажать «Перезагрузка»; если ПК не перезагрузился —
   `journalctl -u ds-agent --no-pager | grep -iE 'sudo|no new priv|effective uid'`.
   OTA службу не обновляет, поэтому на уже установленных ПК правка — вручную.
2. **Токен.** Панель пишет «повторно не показывается», кнопка «Копировать» есть только сразу после
   создания (инструкция 02 описывает кнопку «Скопировать токен» у экрана). При этом
   `GET /minipc/{id}/status` отдаёт все поля экрана, включая токен, под `get_current_admin` — права
   записи не нужно.
3. **Нет офлайн-установки.** Нужны репозитории Astra и PyPI; инструкция упоминает только `.deb`.
4. **Повторный запуск `install.sh`** копирует файлы агента из локальной папки: старая копия откатывает
   версию, обновлённую по OTA.
5. **Команда в панели** (`server/static/js/views/screens.js`) — всегда `http://` и без порта: на
   стенде (8088) и по https она неверна.
6. **Удаление** в инструкции 02 и README не убирает `/etc/sudoers.d/ds-agent-reboot`.
7. **Устаревшая оговорка** в инструкции 02 §5: fullscreen «не проверялся», а на пилоте он подтверждён
   27.07.
8. **Нет тестов** на `install.sh`: он проверяется только на реальном мини-ПК.

## 4. Предложение (черновик, не согласовано)

### 4.1 «Один образ» — флешка автоустановки

Пользователь выбрал «один образ на все ПК» **(решение пользователя)**. Сделать его можно двумя способами:

| | Копия диска пилотного ПК | Флешка автоустановки (`preseed`) |
|---|---|---|
| Что это | Снимок настроенного ПК переносится на остальные | Штатная автоустановка Astra 1.7 с нашими ответами и скриптом донастройки |
| Уникальность ПК | Одинаковые `machine-id`, SSH-ключи хоста, имя, сетевые подключения: перед снимком очистить, при первом запуске создать заново | Каждый ПК ставится с нуля, всё уникально само |
| Железо | Одинаковый режим загрузки, диск не меньше исходного | Разметку делает установщик |
| Лицензия | Неясно, сверить с договором | Официальный способ производителя |
| Время на ПК | Быстрее | Дольше, полная установка |
| Хранение | Большой файл образа | Текстовый файл в git |

**Рекомендую флешку автоустановки (предложение).** Для Astra 1.7 это `preseed.cfg` для debian-installer
(в 1.8 — другой установщик и формат YAML). В файл ответов можно добавить пакеты (`openssh-server`,
`mpv`, `chrony`, `python3-venv`), а команда `preseed/late_command` в конце установки донастраивает
систему. На форумах встречается утверждение, что лицензия Astra запрещает клонировать диски, — не
подтверждено. При автоустановке, по вики Astra, лицензионное соглашение принимается автоматически, а
уровень защищённости нужно выбирать по договору. Сверить с договором может только пользователь.

### 4.2 Автологин без графической утилиты

По вики Astra: в `/etc/X11/fly-dm/fly-dmrc` раскомментировать и задать `AutoLoginEnable=true` и
`AutoLoginUser=<имя>`. База знаний Astra уточняет, что `AutoLoginUser` стоит в секции `[X-:0-Core]`.
При включённых МРД/МКЦ есть параметр `AutoLoginMAC` для метки безопасности при автовходе.

**(догадка)** На пилоте правка через `sed` попала не в ту секцию, поэтому «через файл не работает».
Проверить на пилоте до сборки флешки. `AutoLoginAgain=true` не включать: на пилоте приветствие зависало
на окне отсчёта.

### 4.3 Работа на площадке

Сотрудник ставит ОС, подключает ПК к сети и экрану, адрес — статический; DHCP тоже рассмотреть
**(решение пользователя)**. Порядок **(предложение)**:

1. Сотрудник загружает ПК с флешки. В меню два пункта: «Статический IP» и «DHCP». Установщик сам
   отвечает на все вопросы, кроме сети (для статического — адрес, маска, шлюз, DNS).
2. В конце установки скрипт донастраивает систему: автологин `toor`, отключение блокировки и сна экрана,
   chrony, SSH для техподдержки, `mpv`, служба регистрации с адресом сервера `10.0.119.100`.
3. После перезагрузки на мониторе — экран ожидания: имя ПК, IP, MAC, короткий код и есть ли связь с
   сервером (если нет — почему).
4. Администратор видит в панели «Новый ПК», сверяет по IP или коду, нажимает «Установить агент».
   Экран ожидания сменяется показом.

### 4.4 Статический IP и DHCP **(предложение)**

- **Статический IP** вводится один раз в установщике и не меняется — удобно для техподдержки и сверки с
  планом адресов. Вики Astra в примере удаляет сетевые подключения NetworkManager после установки,
  поэтому надо проверить, что введённый адрес сохраняется в установленной системе.
- **DHCP** не требует ввода. Адрес может меняться — агенту это не мешает, он сам подключается к серверу.
  Для SSH-поддержки адрес лучше закрепить за MAC на DHCP-сервере. В панели ПК отличают по коду с экрана.
- Адрес сервера в обоих вариантах заложен во флешку.

### 4.5 Как агент попадает с сервера

Для чистого ПК реальный путь один — SSH. С подготовленной системой есть вариант лучше.

**Вариант А — ПК сам регистрируется (рекомендую, предложение).** Служба регистрации сообщает серверу
имя, IP, MAC и код; в панели появляется список «Новые ПК». Администратор подтверждает — сервер создаёт
экран и токен, ПК скачивает пакет агента с сервера и ставит его.
- Не нужно вводить IP, на сервере нет ключа ко всем ПК, не нужно открывать в сети направление
  сервер → ПК.
- Представиться «новым ПК» может любое устройство в сети, поэтому токен выдаётся только после
  подтверждения администратором (сверка по коду на мониторе).
- Пакет агента идёт по HTTP без TLS, как и OTA сейчас: в сети его можно подменить. Предлагаю
  подписывать пакет на сервере, а открытый ключ класть на флешку.
- Python-зависимость (`requests`) — внутри пакета, без PyPI. `mpv`, `chrony`, SSH ставятся с флешки.
- Исправление п.1 из §3.2 входит в новую установку.

**Вариант Б — сервер заходит по SSH.** Администратор вводит IP, сервер ключом с флешки заходит на ПК и
запускает установку. Нужен порт 22/tcp от сервера к ПК, а ключ на сервере открывает все ПК.
Предлагаю оставить SSH только для техподдержки, если он нужен.

## 5. Ограничения

- Astra Linux 1.7 SE; пользователь агента `toor`, не root; код агента совместим с Python 3.7.
- Сервер `10.0.119.100`; изолированная сеть, сервер и мини-ПК в одном сегменте LAN. Сейчас открыто
  только направление ПК → сервер: 80/tcp и 123/udp.
- Панель работает только по HTTP: TLS не настроен.
- Пароли нигде не хранить (решение пользователя от 2026-07-09); секреты сервера — только через `.env`.
- Никакого AI/ML — только детерминированная логика.
- Флешку и образ можно собрать и проверить только на железе пользователя; на стороне разработки их не
  запустить.

## 6. Открытые вопросы

1. Как администратор узнаёт ПК? **(догадка)** По плану адресов: сотрудник сообщает, какой IP где
   поставил. Не подтверждено.
2. Сколько ПК и одинаковое ли у них железо (режим загрузки, размер диска)?
3. Какое обновление Astra 1.7, какой уровень защищённости (Орёл / Воронеж / Смоленск), включён ли МКЦ?
4. Есть ли на площадке интернет или локальный репозиторий; в каком репозитории `mpv` — основном или
   расширенном?
5. Нужен ли SSH для техподдержки?
6. Что делать, если адрес сервера сменится?
7. Разрешает ли лицензионный договор выбранный способ установки?

Предложено, но не сделано: скрипт только для чтения, который соберёт эти факты с пилотного ПК
(версия Astra, уровень защищённости, режим загрузки, диск, способ получения IP, `fly-dmrc`, SSH,
наличие `mpv` в репозиториях).
