# 08. Обновление сервера

Сервер обновляется **с самого сервера** (по SSH), а не из панели. Это сделано
намеренно: сервер — это Docker-стек, и его обновление означает пересборку
образов, применение миграций БД и перезапуск контейнеров. Такие операции нельзя
безопасно выполнить «изнутри» панели (API-контейнер не может пересобрать сам себя
без доступа к Docker-сокету хоста — а это дыра в безопасности; и нет пути отката,
если панель упадёт вместе с обновлением). Поэтому — простой и надёжный способ:
одна команда `install_server.sh` на хосте.

> Обновление **агента** — наоборот, из панели (OTA). См. [07_ОБНОВЛЕНИЕ_АГЕНТА.md](07_ОБНОВЛЕНИЕ_АГЕНТА.md).

---

## Про миграции — применяются автоматически ✅
Миграции из `docker-compose.yml` (список `initdb`) применяются только при первом
старте на ПУСТОЙ базе. На **уже работающей** базе новые миграции `docker compose up`
сам НЕ применит — поэтому `install_server.sh` (шаг 5) автоматически вызывает
**`migrate.sh`**, который добивает недостающие миграции.

`migrate.sh` идемпотентен и безопасен при повторном запуске: он ведёт учёт в таблице
`schema_migrations` и применяет только ещё не применённые файлы (а сами миграции —
с `IF NOT EXISTS`/`ON CONFLICT`/`WHERE NOT EXISTS`, т.е. повтор не портит данные).
Сразу после чистой установки он не повторяет то, что уже применил initdb, а
записывает эти файлы в учёт («Учёт миграций начат…»). **Ручные действия с
БД при обновлении больше не нужны** — достаточно положить новый `NNN_*.sql` в
`server/migrations/`.

## Обновление до новой «Бегущей строки» — миграция 034

Миграция `034_ticker_redesign.sql` добавляет в `tickers` срок и «где» (`until_at`,
`target`, кто и когда запустил / правил), создаёт `ticker_groups` и
`ticker_templates` (три стартовых шаблона вставляются, только если таблица пуста)
и колонки отчёта агента в `screens`. Применяется **автоматически** на шаге 5
(`install_server.sh` → `migrate.sh`), ручных действий не нужно. Старые строки
переносятся: **неактивные и истёкшие удаляются**, остальные остаются («все
экраны» или прежние экраны, срок переводится из UTC в МСК, без срока — «до
снятия»). Посмотреть заранее, что будет удалено (только чтение):

```bash
docker exec ds_postgres psql -U display_user -d display_system -c \
  "SELECT id, message, is_active, expires_at FROM tickers WHERE is_active = FALSE OR (expires_at IS NOT NULL AND expires_at <= NOW());"
```

**Порядок.** Миграцию и перезапуск `ds_api` и `ds_celery` делайте **одним
заходом**, то есть обычным `bash install_server.sh` (он пересоберёт и перезапустит
контейнеры, затем применит миграцию). Не применяйте 034 отдельным `bash migrate.sh`,
пока работает **старый** API: после миграции старый код продолжит создавать строки
по-старому — без времени запуска (`started_at`) и с целью «все экраны», даже если
выбраны отдельные экраны; такая строка может сломать сборку ленты экрана. Если
миграцию всё же применили отдельно — сразу перезапустите
`docker compose restart api celery`.

**Что происходит на секундах между перезапуском API и миграцией.** Новый API
стартует раньше, чем `migrate.sh` добавит колонки. Сигналы экранов (heartbeat),
лента, «Стоп» и «Показ» при этом работают — бегущая строка в них изолирована, ошибка
чтения строк не роняет ни сигнал, ни ленту (в ленте тогда нет ключа `tickers`, и
агент 1.4.0 оставляет у себя прежние строки). Страница «Бегущая строка» до конца
миграции отвечает ошибкой — это нормально, обновите её через минуту.

**Если после обновления строка идёт на всех экранах вместо выбранных или в логе
API (`docker compose logs api`) есть «бегущая строка не прочитана».** Проверьте, нет
ли строк без времени запуска:

```bash
docker exec ds_postgres psql -U display_user -d display_system -c \
  "SELECT id, message FROM tickers WHERE started_at IS NULL;"
```

Строки есть → это строки старого API, созданные после миграции. Примените 034
**ещё раз вручную** (файл идемпотентен: трогает только строки с `started_at IS NULL`,
восстанавливает им цель, срок и время запуска, шаблоны не дублирует;
`migrate.sh` второй раз его не запустит — он ведёт учёт):

```bash
docker exec -i ds_postgres psql -U display_user -d display_system < server/migrations/034_ticker_redesign.sql
```

После этого `docker compose restart api celery` не нужен, но страницу стоит обновить.

**Агенты.** Агенты до 1.4.0 продолжают показывать строку по-старому (командами,
одну на экран, без возврата после перезагрузки; в панели — «старый агент — без
подтверждения»). Чтобы строка переживала перезагрузку и появлялось подтверждение
«бежит на X из N», обновите агентов до 1.4.0 по OTA —
[07](07_ОБНОВЛЕНИЕ_АГЕНТА.md#версия-140-бегущая-строка--срочные-объявления).

## Пошагово: обновить сервер

### 1. Подключитесь к серверу и перейдите в каталог проекта
```bash
ssh <пользователь>@10.0.119.100
cd Video_miniPC_v16.2_modular
```

### 2. Сделайте бэкап ПЕРЕД обновлением
```bash
# Дамп БД (в текущий каталог, с датой)
docker exec ds_postgres pg_dump -U display_user display_system > backup_$(date +%Y%m%d_%H%M).sql
```
Медиа и БД лежат в Docker-томах и переживают пересборку контейнеров, но дамп перед
обновлением — обязательная страховка. Полное восстановление — по
[../RESTORE_GUIDE.md](../RESTORE_GUIDE.md).

### 3. Получите новый код
```bash
git pull            # если репозиторий под git
# либо скопируйте новую версию каталога проекта поверх старого,
# СОХРАНИВ существующий .env (в нём пароли и SECRET_KEY)
```
> `.env` **не трогаем и не перезаписываем** — там сгенерированные секреты.

> ⚠ **Если `.env` потерялся** (например, архив распаковали в новый каталог, а
> старый `.env` не перенесли) — `install_server.sh` сгенерирует НОВЫЕ секреты,
> и API перестанет подключаться к БД: том Postgres хранит СТАРЫЙ пароль.
> Симптом: панель не пускает (вход отвечает HTTP 500), в `docker logs ds_api` —
> `password authentication failed for user "display_user"`. Лечение — привести
> пароль в БД к новому `.env` (данные не затрагиваются):
> ```bash
> NEW=$(grep '^DB_PASSWORD=' .env | cut -d= -f2)
> docker exec ds_postgres psql -U display_user -d display_system \
>   -c "ALTER USER display_user WITH PASSWORD '$NEW';"
> docker compose restart api celery
> ```

### 4. Новые миграции — ничего вручную делать не нужно
Если в обновлении появились новые файлы `server/migrations/NNN_*.sql`, они будут
применены **автоматически** на шаге 5 (`install_server.sh` → `migrate.sh`).
Отдельно запускать `psql` не требуется.

> При желании миграции можно применить и вручную (например, без пересборки):
> ```bash
> bash migrate.sh          # идемпотентно, применит только недостающее
> ```

### 5. Пересоберите и перезапустите стек
```bash
bash install_server.sh
```
Скрипт сохранит `.env`, пересоберёт образы, поднимет контейнеры
(`docker compose up -d --build`), **применит недостающие миграции (`migrate.sh`)**
и прогонит самопроверку. Существующие тома (БД, медиа) не затрагиваются.

> Для production-параметров (лимиты памяти, ротация логов) запускайте с override:
> ```bash
> docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
> ```

### 6. Проверьте, что всё поднялось
```bash
docker compose ps            # все 7 контейнеров running/healthy
bash smoke_test.sh           # сквозной прогон (должно быть 0 провалов)
```
Затем откройте панель `http://10.0.119.100/` и войдите.

## Откат, если обновление неудачное
1. Верните предыдущий код:
   ```bash
   git checkout <предыдущий_коммит_или_тег>    # или восстановите старую копию каталога
   ```
2. Пересоберите: `bash install_server.sh`.
3. Если пострадала БД — восстановите из дампа шага 2 по
   [../RESTORE_GUIDE.md](../RESTORE_GUIDE.md).

> Пока вы не запускали `docker compose down -v`, данные (тома `postgres_data`,
> `media_data`, `minio_data`, `backup_data`) на месте. **Флаг `-v` удаляет тома —
> без него не обновляйте.**
