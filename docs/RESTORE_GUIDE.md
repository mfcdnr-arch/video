# Восстановление сервера Digital Signage из резервных копий

Есть три пути. Выбирайте по ситуации:

| Что случилось | Что делать |
|---|---|
| Сервер или его диск погиб, нужно поднять систему на новой машине, а под рукой **копия на флешке** (`ds_copy_*.tar` и `ds_media_*.tar`) | **Сценарий 0** ниже. Основной путь |
| На работающем сервере испорчена база (например, ошибочное массовое удаление) | Сценарий 1 |
| Новая машина, флешки нет, есть только «сырые» бэкапы (дампы из тома `backup_data`, зеркало MinIO) | Сценарий 2 |

Проверено на практике:
- 2026-07-07: дамп БД восстановлен в отдельную базу (28 таблиц, счётчики строк
  совпали), медиафайл выгружен из MinIO с совпадением md5.
- 2026-11-07: **учения по Сценарию 0** на стенде, строго по инструкции из копии
  (подробности — в конце раздела Сценария 0).

## Что и куда бэкапится (автоматически, Celery)

| Что            | Куда                                  | Когда           | Ротация |
|----------------|---------------------------------------|-----------------|---------|
| База данных    | том `backup_data` → `/data/backups/backup_*.sql.gz` | ежедневно 03:30 МСК | последние 14 (env `BACKUP_KEEP`) |
| Медиафайлы     | MinIO, бакет `ds-media-backup`        | ежедневно 02:30 МСК | зеркало (удалённые локально файлы в бакете остаются) |

Обе копии живут в Docker-томах на том же сервере: если погибнет сервер или
его диск, пропадут и они. **Для защиты от гибели самого сервера каждый день
сохраняйте копию на флешку или на свой ПК.** Это делается из панели:
**Настройки → «Копия на флешку»** (видит только супер-администратор; на
дашборде у него же висит ежедневное напоминание). Что внутри копии и как её
скачать — в [руководстве администратора](Инструкции/03_РОЛЬ_АДМИНИСТРАТОР.md),
раздел «Копия на флешку». Копия самодостаточна: по ней систему поднимает и
посторонний человек по инструкции из самого архива (Сценарий 0).

Отдельный дамп можно скачать и из панели: Настройки → «Резервное копирование» →
«Скачать» (только администратор или супер-администратор после входа; прямая
ссылка `/api/backups/{id}/download` без входа отвечает 401). Дамп содержит хеши
паролей и токены всех экранов — храните копии как пароли.

Запасной путь, если панель недоступна: выгрузить тома вручную (на NAS или другую
машину). Пароли сервера (`.env`) этот способ не сохраняет — копируйте файл
`.env` отдельно и храните как пароль.

```bash
# дампы БД
docker cp ds_api:/data/backups ./offsite_backups/
# медиа из MinIO (пример через mc — MinIO Client)
mc alias set ds http://10.0.119.100:9000 <MINIO_USER> <MINIO_PASSWORD>
mc mirror ds/ds-media-backup ./offsite_media/
```

## Сценарий 0: восстановление с флешки (основной)

Для случая, когда старого сервера больше нет (или он не поднимается), а есть
флешка с копией, снятой кнопкой «Копия на флешку». Поднять систему может не
только владелец: **подробная пошаговая инструкция лежит внутри самой копии**, в
файле `ВОССТАНОВЛЕНИЕ.txt` (его видно без пароля, он написан под каждую копию:
дата, адрес сервера, номер миграции, готовые команды). Ниже — краткое содержание
и то, что важно знать заранее. **Идите по `ВОССТАНОВЛЕНИЕ.txt`, а не по этому
пересказу: команды там подставлены под вашу копию.**

**Что нужно**
- Файл `ds_copy_<дата_время>.tar` и **все** файлы `ds_media_*.tar` (ролики лежат
  отдельными архивами: «новые с прошлого раза» и «все»; нужны все, что есть).
- **Пароль на копию** (знает владелец, на флешке его нет). Копия открывается тем
  паролем, который действовал в день её создания. Если пароль забыт, его можно
  сбросить на сервере (`reset_offsite_password.py`), но **старые копии новый
  пароль не откроет**: без своего пароля копию не откроет никто.
- Новая машина с Linux (Astra Linux 1.7 или аналог), Docker Engine с Compose v2,
  интернет (образы Docker скачиваются при установке; офлайн-комплекта пока нет),
  свободного места примерно втрое больше размера всех файлов на флешке.
  OpenSSL — версии 1.1.1 и новее (Astra 1.7 и Debian 10 подходят).
- **Тот же сетевой адрес**, что был у старого сервера: он прописан на всех
  мини-ПК. Старый сервер к этому моменту должен быть выключен. Должны быть
  открыты `80/tcp` (панель и ролики для экранов) и `123/udp` (время).
- Флешка в формате **exFAT или NTFS**: на FAT32 файл больше 4 ГБ не записывается.

**Шаги** (как в `ВОССТАНОВЛЕНИЕ.txt`)
1. **Открыть копию.** Распаковать внешний `tar` в рабочую папку на диске новой
   машины (`~/ds_restore`), проверить `sha256sum -c copy.tar.gz.enc.sha256`,
   снять пароль командой
   `openssl enc -d -aes-256-cbc -pbkdf2 -md sha256 -iter 200000 -in copy.tar.gz.enc -out copy.tar.gz`
   (пароль она спросит сама; «bad decrypt» — пароль неверный), распаковать
   `copy.tar.gz`. Получатся `program/`, `db/`, `documents/`, `media_documents/`,
   `agent_updates/` и `MANIFEST.txt` (опись и контрольные числа из базы).
2. **Поставить программу.** `program/` — это папка проекта вместе с настоящим
   `.env`: переложить её на постоянное место (`~/digital-signage`) и запустить
   `bash install_server.sh`. Существующий `.env` установщик не перезаписывает,
   поэтому пароли и ключи остаются прежними. Поднимется пустой стек.
3. **Вернуть базу.** Один блок команд (он в `ВОССТАНОВЛЕНИЕ.txt`, шаг 4): остановить
   `api` и `celery`, пересоздать базу, залить дамп из `db/` (с `ON_ERROR_STOP`:
   после первой же ошибки остальное не выполняется), применить недостающие
   миграции (`migrate.sh`), запустить `api` и `celery`. В конце должна быть надпись
   **«БАЗА ВОССТАНОВЛЕНА, ПРОГРАММА ЗАПУЩЕНА»**; если вместо неё «ОШИБКА», дальше
   не идти. Блок можно повторять целиком.
4. **Вернуть файлы.** `docker cp`: документы рекламодателей → `/data/backups/documents`,
   файлы OTA → `/data/agent_updates`, папка «Документы» медиатеки → `/data/media`;
   ролики из **всех** `ds_media_*.tar` распаковать в одну папку (имена не
   повторяются) и скопировать в `/data/media`.
5. **Проверить.** Панель открывается, вход со **старым** паролем администратора,
   контрольные числа (экраны, ролики, плейлисты, пользователи, рекламодатели,
   документы) совпадают с `MANIFEST.txt`, экраны сами выходят на связь за
   несколько минут. Старые серверные бэкапы и архивы диагностики в списках
   останутся без файлов (они были на старом сервере) — это нормально.
6. **Убрать за собой.** `rm -rf ~/ds_restore`: в этой папке пароли сервера в
   открытом виде. Папку `~/digital-signage` не удалять — в ней живёт сервер.
   Флешку хранить отдельно от пароля на копию.

**Чего в копии нет:** самих роликов (они в `ds_media_*.tar`), старых ночных
дампов и зеркала MinIO, архивов диагностики экранов. Если архивов роликов у вас
нет, систему всё равно можно поднять, а ролики придётся загрузить в панель заново.

Если что-то не получилось, в конце `ВОССТАНОВЛЕНИЕ.txt` есть раздел «Если что-то
не получилось»; диагностику для того, кто поддерживает систему, собирает
`bash collect_diag.sh`.

### Учения 2026-11-07 (стенд)

Проведены на стенде `dsdev` строго по `ВОССТАНОВЛЕНИЕ.txt`, как их провёл бы
посторонний человек:
- копия и архив «все ролики» скачаны через API панели (так, как их качает
  браузер: по одноразовой ссылке);
- копия расшифрована командой из инструкции в **Debian 10 с OpenSSL 1.1.1n**
  (тот же класс, что Astra 1.7);
- `install_server.sh` из `program/` копии: 21 проверка, 0 предупреждений;
- блок шага 4 закончился надписью «БАЗА ВОССТАНОВЛЕНА, ПРОГРАММА ЗАПУЩЕНА»;
- контрольные числа в базе совпали с `MANIFEST.txt`; md5 роликов (4 файла),
  документов рекламодателей и файлов OTA совпали с исходными; вход со старым
  паролем администратора работает.

Учения нашли настоящую несовместимость: `pg_dump` в образе `api` версии 17, а
сервер БД — PostgreSQL 15, и `pg_dump` 17 пишет в шапку дампа строку
`SET transaction_timeout = 0;`, которую PostgreSQL 15 отвергает. Теперь дамп в
копии на флешку эту строку не содержит, поэтому заливка с `ON_ERROR_STOP` проходит
(про ночные дампы, где строка осталась, — примечание к Сценарию 1).

**Не покрыто учениями:** настоящая машина Astra Linux, настоящая флешка и браузер
на ПК оператора (в автотесте панели скачивание идёт в безголовый Chromium без
выбора места сохранения). Прогнать Сценарий 0 на настоящей Astra стоит один раз
до того, как он понадобится всерьёз.

## Сценарий 1: восстановление БД на работающем сервере

Например, после ошибочного массового удаления.

```bash
cd Video_miniPC_v16.2_modular

# 1. Выбрать дамп
docker exec ds_api ls -t /data/backups/

# 2. Остановить api и celery, чтобы никто не писал в базу
docker compose stop api celery

# 3. Пересоздать базу и залить дамп
docker exec ds_postgres psql -U display_user -d postgres \
  -c "DROP DATABASE display_system" \
  -c "CREATE DATABASE display_system OWNER display_user"
docker exec ds_api sh -c "gunzip -c /data/backups/ИМЯ_ДАМПА.sql.gz" \
  | docker exec -i ds_postgres psql -U display_user -d display_system -q

# 4. Запустить обратно и проверить
docker compose start api celery
docker exec ds_api curl -s http://localhost:8000/health
```

Имена базы/пользователя возьмите из своего `.env` (`POSTGRES_DB`,
`POSTGRES_USER`) — выше показаны значения по умолчанию.

> **Одна безвредная ошибка при заливке.** `pg_dump` в образе `api` новее сервера
> БД (17 против PostgreSQL 15), поэтому **ночные и ручные дампы** (раздел
> «Резервное копирование» в Настройках, том `backup_data`) начинаются со строки
> `SET transaction_timeout = 0;`. PostgreSQL 15 её не знает и при заливке
> печатает одну строку `ERROR:  unrecognized configuration parameter
> "transaction_timeout"`. Это нормально: команды выше (без `ON_ERROR_STOP`) на
> неё не останавливаются, и остальной дамп заливается целиком. Любые другие
> ошибки игнорировать нельзя. (В дампе внутри копии на флешку этой строки нет,
> поэтому в Сценарии 0 такой ошибки не бывает.)

## Сценарий 2: полное восстановление на новой машине

Это ручной путь «из сырых бэкапов». Если у вас есть копия на флешке, проще и
надёжнее Сценарий 0: он возвращает и `.env` (пароли сервера), и файлы OTA,
которых в сырых бэкапах нет, и не заставляет собирать части из разных мест.

1. Установить Docker, скопировать папку проекта на новый сервер.
2. `bash install_server.sh --env-only` — создаст новый `.env`
   (или скопируйте сохранённый старый `.env` — тогда пароли и токены
   входа останутся прежними).
3. `bash install_server.sh` — поднимет пустой рабочий стек.
4. Восстановить БД по Сценарию 1 (дамп принести с собой / со внешней копии).
   ВАЖНО: токены экранов лежат в базе, поэтому после восстановления БД
   все мини-ПК продолжат работать без перенастройки — им нужен только
   прежний IP/домен сервера (он прописан в конфиге агента).
5. Восстановить медиафайлы в том `media_data`:
   ```bash
   # если старый MinIO жив (бэкапный том переехал или доступен по сети):
   docker exec ds_celery python3 - <<'EOF'
   from minio import Minio
   import os
   c = Minio(os.getenv("MINIO_ENDPOINT", "minio:9000"),
             access_key=os.getenv("MINIO_USER"),
             secret_key=os.getenv("MINIO_PASSWORD"), secure=False)
   for obj in c.list_objects("ds-media-backup", recursive=True):
       c.fget_object("ds-media-backup", obj.object_name,
                     "/data/media/" + obj.object_name)
       print("восстановлен:", obj.object_name)
   EOF
   # либо из внешней копии: docker cp ./offsite_media/. ds_api:/data/media/
   ```
6. Проверить: панель открывается, медиатека показывает ролики
   (миниатюры пересоздадутся сами при первом просмотре), экраны выходят
   на связь, `Отчёты` показывают историю.

## Регулярная проверка (раз в квартал)

Бэкап, из которого ни разу не восстанавливались — это не бэкап.
Быстрая проверка без остановки сервера (безопасно, работает во
временной базе):

```bash
LATEST=$(docker exec ds_postgres psql -U display_user -d display_system \
  -tAc "SELECT filename FROM backups ORDER BY created_at DESC LIMIT 1")
docker exec ds_postgres createdb -U display_user restore_test
docker exec ds_api sh -c "gunzip -c /data/backups/$LATEST" \
  | docker exec -i ds_postgres psql -U display_user -d restore_test -q
docker exec ds_postgres psql -U display_user -d restore_test \
  -c "SELECT COUNT(*) AS tables FROM information_schema.tables WHERE table_schema='public'"
docker exec ds_postgres psql -U display_user -d display_system -c "DROP DATABASE restore_test"
```

Ожидаемо: количество таблиц совпадает с рабочей базой (28 на момент
написания), при заливке нет ошибок, кроме одной безвредной строки про
`transaction_timeout` (см. примечание к Сценарию 1).

Копию на флешку тоже стоит проверять: раз в квартал откройте свежую
`ds_copy_*.tar` по первым шагам Сценария 0 (распаковать, проверить `sha256sum`,
снять пароль) и сверьте `MANIFEST.txt` с панелью. Если пароль на копию не
подошёл, узнать об этом нужно сейчас, а не в день аварии.
